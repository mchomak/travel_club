# Спецификация: анкеты перелётов и проживания, редактирование дня

## Задача

При создании поездки пользователю неудобно заполнять перелёты и проживание в боковой панели, отдельно от общего календаря. После завершения мастера редактирование дня из полного календаря также не открывает дневной редактор.

## Решение

На этапе 2 формы перелётов, а на этапе 3 формы проживания размещаются на странице конструктора под соответствующими строками. Кнопки добавления перелёта и проживания открывают полную форму соответствующего элемента прямо в этой строке. Под списком форм остаётся полный календарь поездки, который показывает те же данные и обновляется после сохранения элемента в общем черновике.

При выборе города перелёта страна подставляется из метаданных подсказки. В списке подсказок доступны также страны и города, уже выбранные в перелётах этой поездки. У перелёта убирается отдельное текстовое поле «Маршрут / аэропорты».

Карандаш дня в полном календаре полного редактора сохраняет текущие изменения и открывает редактор поездки на этапе 4 с выбранным днём. На странице видны полный календарь, календарь только выбранного дня, программа дня, карта и остальные разделы этапа 4.

## Решения по реализации

1. Этап 2 встраивает существующую `ItemForm` только для перелётов, этап 3 — только для проживания; дальние переезды/поезда/автобусы на этапе 2 продолжают открываться прежним способом. Для перелёта и проживания сохраняются все прежние функции формы: все прежние поля, варианты элемента, места на карте, время/даты, расчёт, цена/валюта/курс, заметки, действия сохранения/отмены/удаления, значения по умолчанию и проверки остаются; единственное исключение — текстовый маршрут перелёта по R07. Новая таблица, отдельная копия маршрута или отдельный расчёт не вводятся: `TripEditor` остаётся владельцем черновика и сохранения.
2. В `TripBuilder` элементы отображаются строками с одной открытой встроенной формой одновременно. Добавление создаёт локальное состояние формы; TripInput меняется после явного сохранения. При незавершённой форме переход/добавление не уничтожает ввод: нужно сохранить или отменить её.
3. Общий календарь рендерится под формами и получает полные дни и элементы. Формулы, дневное распределение, ночёвки, переносы и прочие действия календаря остаются существующими.
4. Историю стран и городов `CountryCity` получает как производный список из `departure_country_code/departure_city` и `arrival_country_code/arrival_city` сохранённых элементов типа flight. Значения уникальны в рамках пары страны/города и не пишутся отдельно в БД.
5. Выдача `/maps/search?kind=city` несёт ISO `country_code` для каждого варианта, который показывается как выбираемый город; вариант без кода не предлагается как подтверждённый город. Выбор варианта из поиска или истории обновляет город и страну атомарно. Свободный текст не считается разрешённым городом, поэтому пользователь вручную задаёт страну.
6. Убирается только свободное текстовое поле `location` с подписью «Маршрут / аэропорты» для flight. Сохранённые старые значения и отдельные структурированные поля карты не удаляются. Поле location у других типов элементов не меняется.
7. Полный редактор направляет карандаш дня на `/admin/trips/{id}/builder?step=4&day={dayId}` через общий путь сохранения перед навигацией. Builder уже показывает полный TripCalendar и ниже ограниченный одним днём календарь с программой и картой.
8. Основная ветка — `origin/master`, указанная `origin/HEAD` в этом checkout; commit и push выполняются после проверок. База данных, денежные формулы и API поездки не меняются. Результат поиска городов дополняется полем `country_code`; для вариантов, которые UI предлагает выбрать, код обязателен. Миграция не требуется.
9. При навигации или смене шага ошибка сохранения оставляет пользователя на текущем экране; unsaved form не теряется без явного отмены. Существующие аутентификация, клиентский preview и API сохранения сохраняются.

## Границы и швы

| Модуль | Владеет | Выставляет | Прячет |
|---|---|---|---|
| `TripEditor` / `DraftSession` | Единым черновиком, открытой inline-формой, обновлением и сохранением поездки | Текущую строку формы для builder; `save` перед переходом к шагу 4 | Очередность сохранения, сверку версии с сервером и сетевые ошибки |
| `TripBuilder` | Строками на этапах 2–3, состояниями пустого списка и местом для формы | `renderItemForm(itemId)` для единственного активного элемента; добавление/редактирование/удаление через существующие callbacks | Финансовые расчёты и сохранение |
| `ItemForm` | Валидацией и полями одного элемента | Существующие `onSubmit`, `onCancel`, `onDirtyChange`; inline-размещение в builder | Черновик поездки и persistence |
| `CountryCity` | Контролируемой парой страны и города, поиском и быстрыми вариантами | `onChange(countryCode, city)`; проп `history: PreviousFlightPlace[]` | Формирование истории из поездки и хранение маршрута |
| Maps search | Преобразованием ответа геокодера и поиском городов | Опциональный `country_code` в результатах города | Секрет провайдера и формат его ответа |
| `TripCalendar` | Отображением и взаимодействиями общего/дневного календаря | Существующий `onEditDay(dayId)` и события календаря | Переходами между страницами и сохранением |

**Швы для тестов:** `CountryCity` controlled props и результат `mapsClient.searchCities`; `TripBuilder` с подменёнными callbacks и рендером формы; `TripEditor` + существующие `DraftSession`/Trip API; callback `TripCalendar.onEditDay`. Интеграционный сценарий проверяет цепочку анкета → общий календарь → сохранение → повторное открытие → карандаш дня → builder на выбранном дне. Backend parsing `country_code` проверяется на ответе `/maps/search`.

## Вне рамок

- В рамках R05/R06 не добавляются отдельные постоянные справочники и таблицы городов/стран; быстрый список строится только из перелётов текущей поездки.
- Не меняются ценообразование, формулы сметы, база данных и сохранение поездки; новые внешние сервисы и зависимости не нужны.
- Публичные страницы, клиентский preview и полный режим редактирования элементов в боковой панели вне этапов 2–3 сохраняют прежнее поведение.
