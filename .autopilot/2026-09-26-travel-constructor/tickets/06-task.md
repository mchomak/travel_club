# 06 — Распределить многодневные расходы по дневной смете

**Требования:** R253, R255, R552 (критерий 16), D02

**Blocked by:** 05

**Зона:** `backend/app/`, `backend/tests/`, `frontend/src/lib/`, `frontend/src/components/trips/`, `frontend/e2e/`, `shared/pricing-vectors.json`, `README.md`, `docs/acceptance.md`

**Волна:** 5

**Status:** ready

## Что должно заработать

Слепая G4-приёмка по исходному брифу нашла расхождение: для `per_day` и `per_person_per_day` расчёт охватывает несколько дней, но весь расход показывается в выбранном первом дне. Исправить дневную смету по уточнению `spec.md` «G4 / D02»: элемент с `day_id` относится к последовательным датам в количестве `duration_days` начиная с назначенного дня, без повторного увеличения общей себестоимости; элемент без `day_id` остаётся общим расходом. Если длительность не помещается в поездку, API возвращает понятную ошибку, UI помогает исправить данные. Сохранить parity Python/TypeScript и исторические snapshots. Никаких изменений семи первичных формул, кроме распределения рассчитанной суммы по дням.

## Из брифа, дословно

> «Многодневные расходы должны отображаться логично.»
>
> «Но при этом итог путешествия всегда должен рассчитываться из первичных статей затрат, чтобы распределение по дням не приводило к двойному учёту.»
>
> «16. Увидеть стоимость каждого дня.»

## Разделы спецификации

`spec.md` §11, §13 и «Уточнение G4 / D02 — многодневная дневная смета». `interfaces.md` — финансовый Calculation contract.

## Критерии приёмки

- [ ] `per_day` и `per_person_per_day` с `day_id` распределяются по последовательным дням; каждый день показывает правильную категорию и вклад, в том числе при разных валютах/подгруппе/количестве.
- [ ] Сумма дневных групп + общие расходы точно равна `cost_total`, а сумма первичных статей не увеличивается из-за отображения по дням; `included=false` не учитывается.
- [ ] Пограничные малые суммы и округление до копейки не дают отрицательных долей; контрольные векторы общие для backend/frontend.
- [ ] Длительность, выходящая за даты поездки, явно отклоняется без потери введённого; сокращение дат не уничтожает данные молча. При необходимости учесть уже сохранённые документы с прежней семантикой и описать подход.
- [ ] Backend API, frontend preview и браузерный сценарий проверяют дневные итоги, повторное открытие, изменение количества участников, и parity обеих реализаций.
- [ ] README и матрица приёмки отражают фактическое правило. Backend pytest/Ruff, frontend unit/ESLint/typecheck/build и Playwright проходят.
