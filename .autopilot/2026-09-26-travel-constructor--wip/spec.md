# Спецификация: Travel Club

## Задача и решение
Василиса собирает международный маршрут без ручной математики и потери данных. Закрытая панель хранит поездки в PostgreSQL, показывает расписание и проверенную смету, позволяет повторно открыть, изменить и скопировать маршрут. Все обязательства исходного брифа сохраняются. Нумерация ниже соответствует его разделам; точная трассировка каждого исходного фрагмента — в таблице покрытия в конце.

## §0–2. Результат и границы продукта
Рабочее приложение, не макет. Модульный монолит с независимыми слоями интерфейса, HTTP API, ORM, auth и расчётного домена. Локальный запуск одним Docker Compose. Пустая база — содержательный пустой список с действием создания, без придуманных реальных цен и маршрутов. Ошибки загрузки имеют повтор, пустой список отличим от ошибки.

## §3. Стек и запуск
Python 3.12+ в Docker, FastAPI, SQLAlchemy 2, Alembic, psycopg 3, Pydantic 2, pytest, Ruff. Next.js App Router, React, TypeScript strict, Tailwind; React Hook Form + Zod для сложных форм, TanStack Query для серверного состояния. Зависимости последних стабильных совместимых выпусков уточнить в официальных реестрах и зафиксировать lock/requirements. Три сервиса: frontend, backend, postgres (стабильный PostgreSQL). Данные в named volume; .env игнорируется, .env.example без действительных секретов; настройки проверки production cookie; миграции автоматически до API. Секреты пользователь вводит локально, не в чат. Никаких платных сервисов.

## §4. Экраны
Публичная лёгкая группа: `/`, `/tours`, `/services/route`, `/services/turnkey`, `/payment` — честные заглушки без работающей оплаты или регистрации. Административная группа отдельно: `/admin/login`, `/admin/trips`, `/admin/trips/new`, `/admin/trips/[id]`, защищённый клиентский preview `/admin/trips/[id]/preview`. Публичная и административная разметки независимы; future rich media возможно добавить только в публичную группу.

## §5. Авторизация
User: UUID, уникальный нормализованный login, Argon2id password_hash, created_at. Серверные сессии: случайный токен, только SHA-256 digest хранится в таблице Session, user_id, expires_at. Cookie HttpOnly, SameSite=Lax, Secure в production, ограниченный срок (12 часов). Logout удаляет сессию и cookie. Login одинаковая понятная ошибка для неизвестного логина и неверного пароля. Сервер ограничивает повторные попытки (персистентные записи LoginAttempt, лимит для логина и IP). Не доверять произвольному X-Forwarded-For. Все private API через dependency require_admin. Защита unsafe методов от CSRF: обязательный X-Requested-With: TravelClub, проверка Origin, если присутствует, только настроенный origin; CORS не разрешает чужие origin. Авторизация на сервере Next перед отдачей приватных страниц, redirect на login при 401; API всегда независимо защищено. Login/logout/me; bootstrap admin через CLI с getpass или переменные окружения, никогда дефолтный известный пароль. Production конфигурация не может случайно разрешать insecure cookie.

## §6. Поездка
Trip хранит id, internal_title, client_title, start_date/end_date включительно, participants > 0, base_currency, internal_note, client_note, status draft/ready/archived, pricing_mode markup/target_margin, pricing_percent, created_by, created_at/updated_at, version, cost_total/client_price/profit. Создание генерирует каждый календарный день. Даты и число дней видны; финансовые поля доступны лишь через серверный расчёт. При пустой смете cost=price=profit=0 и actual_margin=0; нет деления на ноль.

## §7–8. Дни и таймлайн
TripDay: UUID, trip_id, date, country, city, place, title, internal_note, client_note. Один день на дату, строго внутри диапазона. Ряд/список дней с выбранным днём и числом элементов; дневной таймлайн с временем, названием, местом, типом, стоимостью. Можно открыть любой день, редактировать локации и заметки, добавить/изменить/удалить элемент с подтверждением, задать необязательное start_time/end_time, название/описание/место/заметки. Время локальное для данного места; end_time должен быть не раньше start_time, перелёт через полночь может оставаться без end_time с пояснением в описании. Порядок задаётся кнопками вверх/вниз независимо от времени; перенос — выбор другого дня или «Общие расходы». UUID и enum в пользовательских подписях не видны. Удаление элемента спрашивает подтверждение, отмена сохраняет форму.

## §9. Типы
flight, train_bus, transfer, hotel, excursion, activity, rental, insurance, other. Девять русских кнопок. Default modes: flight/train_bus/activity/excursion → per_person, transfer → capacity, hotel → hotel, rental → per_day, insurance → per_person_per_day, other → fixed. Любой тип может выбрать любое правило, поля показываются по правилу. Единая таблица TripItem; нет девяти подсистем.

## §10–11. Расчёт
TripItem: UUID, trip_id, day_id nullable, position, type, title, description, location, start_time/end_time, internal_note/client_note, included, currency, unit_price Decimal, quantity Decimal>0, participants_override nullable positive int, capacity positive int nullable, rooms_override positive int nullable, duration_days positive int, check_in/check_out nullable. Финансовые snapshots: original_amount, rate_used, normalized_amount — NUMERIC. null override значит всех участников поездки; явная подгруппа не больше trip.participants, при его уменьшении противоречие отклоняется с подсказкой. Цена неотрицательная, бесплатный элемент допустим. NaN/Infinity/отрицательные и некорректные значения запрещены; разумные лимиты входов для защиты вычислений.

Единый чистый доменный `calculate_trip(TripInput) -> Calculation`:
- per_person = unit_price × effective_people × quantity;
- fixed = unit_price × quantity;
- capacity = unit_price × ceil(effective_people / capacity) × quantity;
- hotel = unit_price × (rooms_override или ceil(effective_people / capacity)) × (check_out - check_in).days; quantity не умножает гостиницу;
- per_day = unit_price × duration_days × quantity;
- per_person_per_day = unit_price × effective_people × duration_days × quantity;
- manual = unit_price (в UI «Итоговая сумма»), игнорируя неактивные поля.
Неактивные поля не влияют на расчёт. Отель требует заезд < выезд, внутри [trip.start, trip.end+1 день], day_id соответствует заезду или null; без неявного изменения дат отеля. Округление HALF_UP: original_amount до .01, затем original_amount × rate до .01; все суммы и проценты JSON строки. В БД Numeric для денег и курсов, отсутствие float в финансовом домене. Границы суммы, количества и курса согласованы с Numeric. included=false сохраняет элемент и рассчитанную стоимость, но даёт нулевой вклад в итоги. UI это отмечает.

## §12. Валюты
Коды ISO-подобные `[A-Z]{3}`, не ограничены перечнем. Курс: стоимость 1 единицы валюты статьи в базовой, >0. Base rate всегда 1; TripCurrencyRate уникальна по trip/currency. UI объясняет направление, предлагает RUB/USD/EUR/CNY/TRY/THB и ввод собственного кода. Неизвестный курс блокирует достоверный расчёт/сохранение с указанием валюты; не подставлять 1. Изменение курса пересчитывает все snapshots и итоги транзакционно. При смене базы старые курсы не переиспользуются как новые: пользователь заново подтверждает/вводит необходимые курсы, иначе save не проходит. Исторически сохранённый маршрут воспроизводится из сохранённых статей и курсов, внешнего FX нет.

## §13. Дневная смета
Проживание распределяется по ночам, без дня выезда. После округления равные доли, остаток в последнюю ночь. Итого поездки — сумма первичных included статей, а не элементов плюс дневных распределений. Остальные дневные статьи относятся к назначенному дню, per_day длительность в подсказке. day_id=null для общих расходов: отдельный subtotal, кроме гостиницы с известными ночами, которая распределяется по ночам. Для каждого дня четыре группы: транспорт (flight/train_bus/transfer/rental), проживание, активности (excursion/activity), прочее (insurance/other), сумма. Сумма дневных итогов + general_total == cost_total. Item totals не дублируются при многодневном отображении.

## §14–15. Финансовая сводка
Постоянно доступная sticky панель на desktop, обычный доступный блок на узком экране. cost_total, cost_per_person; разбивка по каждому типу расходов (девять типов можно визуально объединить train_bus/rental как транспорт), наценка/целевая маржинальность с пояснением, client_price, profit, actual_margin_percent, client_price_per_person. markup: price=round(cost×(1+percent/100)); target_margin: price=round(cost/(1-percent/100)), 0<=percent<100. Markup >=0 с ограничением на overflow. Profit=price-cost; actual_margin=profit/price×100 или 0 при price=0. Налоги/комиссии/маркетинг/сопровождающие не добавляются. Результат домена пригоден как вход будущей модели групповых туров.

## §16–17. Заметки и сохранение
Обычный текст trip/day/item, internal и client разделены явно. Autosave после валидных изменений с задержкой около 800ms; «Есть изменения», «Сохранение…», «Сохранено», «Не удалось сохранить» плюс явная кнопка и повтор. Редактируемый черновик не заменяется запоздалым серверным ответом; запросы сериализованы, только последний соответствует текущей версии. После ошибки поля остаются на экране, переход/закрытие с dirty вызывает предупреждение; preview ждёт успешного save. Сохранение атомарно целого агрегата (включая days/items/rates), ответ — актуальный агрегат+calculation+version. Version mismatch даёт 409 без перезаписи, ясное предложение перечитать после предупреждения о локальных изменениях. Нельзя сообщать «Сохранено» до успешного HTTP ответа. При перезагрузке ранее сохранённые данные полностью восстанавливаются. Создание формы выполняется только явной кнопкой один раз, защитить double submit; после create переход к UUID.

## §18. Список
Название, уникальные страны/города по порядку дней, даты, люди, себестоимость, клиентская цена, статус, изменено. Создать, открыть, duplicate (новые UUID всех сущностей, title «… — копия», собственная версия, суммы те же), archive/restore, delete с подтверждением. Копия независима: её правка не меняет оригинал. Loading/error/empty состояния. Удаление атомарно каскадное, всегда через явное действие.

## §19. Preview
Отдельный authenticated endpoint и строгая allowlist schema: client_title (fallback internal title), dates, participants, локации, дни, элементы с типом/названием/временем/описанием/местом/client_note. Общие нефинансовые элементы показываются отдельным разделом. Никогда internal_note, unit_price, rates, cost, markup, profit — ни в JSON preview, ни в DOM. Preview внутри приватной панели; публичная ссылка отсутствует. Понятная кнопка обратно к редактированию, визуальная иерархия и пригодность к печати.

## §20. Схема БД
User, Session, LoginAttempt; Trip; TripDay UNIQUE(trip_id,date); TripItem с FK на Trip и nullable день той же поездки, индексы trip_id/day_id; TripCurrencyRate UNIQUE(trip_id,currency). UUID идентификаторы, timestamptz audit. Trip owner для атрибуции, все авторизованные администраторы могут редактировать все поездки. SQL FK cascade; проверка принадлежности вложенных id, недопустимость чужих/повторных UUID. Numeric(20,2) деньги, Numeric(20,8) курсы, количественные Numeric. Alembic начальная миграция и проверка чистой PostgreSQL. Не хранить бизнес-агрегат одним JSON blob.

## §21. Контракты и границы
Все пути `/api`, Next same-origin proxy в backend. `GET /health` без секрета; `POST /auth/login {login,password}`, `POST /auth/logout`, `GET /auth/me -> {id,login}`. `GET /trips -> TripSummary[]`; `POST /trips` начальные trip fields → TripDocument; `GET /trips/{id}` → TripDocument; `PUT /trips/{id}?confirm_date_removal=false` полная editable TripInput + version → TripDocument; `DELETE /trips/{id}` →204; `POST /trips/{id}/duplicate` → TripDocument; status через PUT; `POST /trips/calculate` валидируемый TripInput → Calculation; `GET /trips/{id}/preview` → ClientPreview. Дни/элементы/порядок/перенос/курсы CRUD атомарно внутри PUT без формального размножения endpoint. Отсутствующий trip 404, validation 422 с человеческим message, date loss и version conflict 409 с кодом и данными для UI. Никаких traceback клиенту.

| Модуль | Владеет | Выставляет | Прячет |
|---|---|---|---|
| Pricing | семью формулами, FX, округлением, распределением, сводкой | calculate_trip(TripInput) -> Calculation | Decimal арифметику и порядок округления |
| Trip service | агрегатом PostgreSQL и инвариантами дат/версий/копирования | перечисленные REST CRUD endpoints | ORM, транзакции, snapshots |
| Auth | пользователями и сессиями | login/logout/me, require_admin | Argon2id, токены, throttling |
| Frontend API | сетевым обменом и сериализацией | типизированный client для REST, TripDocument | transport, CSRF header, ошибки |
| Editor | локальным черновиком и autosave | экраны editor/list/preview | формы, dirty/version handling |
| Preview calculator | мгновенным предварительным выводом | calculateTrip(TripInput) -> Calculation | decimal.js, те же правила; контрольные векторы обязательны |

Швы тестов: чистый calculate_trip и тот же контракт через calculateTrip; HTTP API с реальной PostgreSQL; браузерные пользовательские сценарии.

## §22–23. Изменения зависимостей
При расширении диапазона backend создаёт пустые даты. При сокращении сохраняет пересечение, удаляет пустые дни автоматически, но заполненные дни/элементы требуют 409 DATE_REMOVAL_REQUIRED со списком дат и повторного запроса confirm_date_removal=true после явного confirm пользователя. Сам факт отсутствия дня в payload не служит согласием. Нельзя обходить защиту удалением массива days. Попавшие за границы гостиницы требуют исправить даты/удалить подтверждённо, не молча обрезать. Смена people/rates/mode/date сразу меняет local preview и окончательный серверный результат. Фиксированные расходы не зависят от people, явный people override сохраняется.

## §24–27. UX, адаптивность и ошибки
Спокойная тёплая светлая рабочая поверхность, графитовый текст, глубокий зелёный акцент, аккуратные линии маршрута, умеренные радиусы, без фотобаннеров/3D. Лёгкий левый nav, header параметров, day rail/timeline, справа деньги. Label над каждым полем; keyboard focus видим, modal имеет focus trap/Escape и возврат фокуса, ошибки связаны с полями, статусы aria-live. Mobile: панели складываются, формы без горизонтального overflow, основные действия доступны. Несколько десятков элементов не превращаются в сетку бухгалтерских колонок. Сложные поля через «Дополнительно», defaults по типу, подсказки для вместимости/комнат/FX/наценки. Формы не очищаются при ошибке; сохранение/расчёт/авторизация имеют русские объяснения. Не показывать raw enum, JSON или stack trace. Server exceptions журналируются без паролей/токенов.

## §28–30. Проверки качества
Обязательные deterministic vectors: flight 35000×3=105000; transfer 4000 capacity4 people3/4/5/8/9=4000/4000/8000/8000/12000; hotel 10000 people5 cap2 nights4=120000; activity 2000×5=10000; fixed 15000 независимо от people. Дополнительно семь правил, manual override rooms/people, исключение расходов, валюты/изменение курса, midpoint rounding, остаток дневного распределения, margin vs markup, zero/negative/NaN, capacity0, пустая поездка, сокращение диапазона, duplicate независимость, autosave conflict, неавторизованные запросы, cookie/logout/rate limit, preview redaction, persistence after reopen. Общие JSON fixtures для Python и TS; не дублировать формулы в компонентах. Backend lint/pytest, frontend eslint/typecheck/unit tests/production build; миграции на чистой PostgreSQL; Compose startup; браузер login/create/edit/reopen/preview и адаптивная проверка.

## §31–32. Вне рамок
Публичный полноценный дизайн, платёжные системы/банки, bookings, flight/hotel/FX API, CRM, сложные роли, регистрация, 3D, мобильное приложение, налоги/бухгалтерия, сопровождающие/маркетинг/комиссии/резервы и полный калькулятор экономики тура не реализуются по прямому указанию брифа. Независимые public/admin layouts, reusable pricing и preview DTO позволяют добавлять их позднее. Никаких иных отложенных требований текущего этапа.

## Уточнения независимой проверки G2 (нормативные)

- Распределение по ночам зависит от `calculation_mode=hotel`, а не от типа. `type=hotel` с manual/fixed без гостиничной формулы относится целиком к выбранному дню либо общим расходам; UI явно говорит «Вся сумма в выбранный день». Любой другой тип с формулой hotel распределяется по ночам и сохраняет свою категорию. Это уточнение заменяет общее слово «проживание» в §13 там, где речь о распределении.
- Allowlist preview включает `client_note` на всех трёх уровнях: поездка, день, элемент; интерфейс показывает каждую непустую заметку. Внутренние заметки по-прежнему исключены.
- Время окончания меньше начала разрешено и означает следующий календарный день; UI показывает «на следующий день». Это заменяет запрет из §7–8. Оба времени сохраняются структурированно; пояснение в описании не требуется. Для более длинных перемещений описание может уточнять длительность; текущий бриф не требует многодневного часового расписания.
- Дополнительные отдельные возможности `restore` и `client_price_per_person` исключены из обязательного объёма: статус остаётся редактируемым обычным способом, сводка на человека относится к себестоимости.

## Уточнение D01 — распределение малых сумм проживания

Для неотрицательной нормализованной суммы T и n ночей первая доля равна HALF_UP(T/n, .01). При n > 1 её ограничивают сверху floor(T/(n−1), .01), чтобы остаток последней ночи не стал отрицательным. Первые n−1 ночей получают эту долю, последняя T − доля × (n−1). При одной ночи вся сумма относится к ней. Например .02 на четыре ночи: 0, 0, 0, .02. Это уточняет правило «округлённые равные доли, остаток в последнюю ночь» без изменения итоговой стоимости; Python и TypeScript проверяются общими векторами.
