# Спецификация: разделение репозитория

## Результат и границы

Три самостоятельных Next.js-приложения npm в `apps/website`, `apps/trip-constructor`, `apps/interviews`; каждое владеет собственными маршрутами, настройками, CSS, шрифтами, визуальными компонентами, ресурсами и тестами. Никаких межпродуктовых визуальных импортов. Нейтральный общий код допускается только при подтверждённой потребности. Существующий FastAPI, PostgreSQL, модели, миграции, авторизация и формулы остаются едиными источниками истины.

## Контракт поведения

1. Website сохраняет все действующие публичные маршруты и главную на `/` на основе test_21, переименованные компоненты, активные изображения и IndexedDB редактора. При инвентаризации явно сверяются ожидаемые пути `/`, `/formats`, `/services/*`, `/archive`, `/archive/[slug]`, `/tours`, `/tours/[slug]`, `/start`, `/thanks` и юридические/служебные страницы с фактическими маршрутами; отсутствующие detail routes не создаются. `/test_21` удаляется либо остаётся только noindex. Все публичные страницы используют утверждённую систему, включая Lato; это уточнение пользователя допускает соответствующее изменение типографики старых страниц. Не выдумывать новый Pantone Cloud.
2. Constructor сохраняет `/admin/**`, клиентский просмотр, создание, редактирование, календарь, карту, шаги и расчёты; Interviews сохраняет `/research/**`, анкеты, сценарии, ответы, версии, экспорт и защиту admin. Фактическая принадлежность `/home` устанавливается по текущим маршрутам, ссылкам, runtime и auth, а не по имени; существующий контракт проекта указывает на защищённый каталог Constructor, его следует подтвердить и сохранить, если инвентаризация не выявит противоречий. Поведение и данные не переписываются.
3. На общем origin входящие `/research/**` направляются Interviews, `/admin/**` и `/home` — Constructor при подтверждении фактической принадлежности, остальные публичные маршруты — Website; `/api/**` идёт в имеющийся backend. Прокси сохраняет методы, тела, заголовки и host-only cookie. Для локального самостоятельного запуска каждый private frontend имеет работающий путь к backend и входу без запуска двух других. Разные статические ресурсы Next и `public/` должны быть адресованы без конфликтов. Не вводить внешний домен и не объявлять production deployment выполненным.
4. До удаления архивируются только действующие маршруты, соответствующие запросу `/test_1`–`/test_19`, после точной инвентаризации путей и зависимостей. Не подменять этот перечень `/test` или `/test_20` без подтверждения, что это одна из заказанных версий; отсутствующие маршруты не создавать. `/test_20` проверяется отдельно по условию пользователя. Сохраняются живые зависимости, пока они используются, с нормальными именами в собственном приложении. Архивная документация раскрывает фактическое отсутствие `/test_1` и историю версий, если это подтвердится. GitHub Release готовится по проверенному содержимому без раскрытия чувствительной информации. История Git не переписывается, чужие изменения не стираются и не включаются в архивные коммиты.
5. Три набора корневых глобальных стилей и дизайн-систем независимы. Constructor и Interviews сохраняют внешний вид; временное изменение токена каждого приложения с проверкой остальных и обязательным восстановлением демонстрирует изоляцию. На Website адаптер всех страниц использует утверждённые токены и локальные Lato-файлы.
6. Корневые npm-команды запускают, собирают и проверяют приложения по отдельности и все вместе. Зафиксированы доступные порты, `.env.example` каждого приложения и происхождение общих backend-переменных. Запуск одного frontend не требует запуска остальных; backend требуется только там, где требуется существующая функциональность.
7. Исходная карта, архитектура, восстановление из тега, runbooks и README приложений документируют фактическое состояние, ограничения и маршрутизацию. Существующая конфигурация развёртывания не меняет публичный домен или данные; отсутствие CI не оправдывает сложную новую инфраструктуру.
8. Приёмка включает lint/typecheck/build и тесты каждого приложения, все основные маршруты, авторизацию, браузерную консоль и запросы, адаптивность, ссылки и ресурсы, бизнес-сценарии Constructor и Interviews, API/БД, CSS-изоляцию и регрессии. Любую недоступную проверку назвать, не представлять как пройденную. Базы не очищать, пользовательские данные не удалять.

## Границы и швы

| Единица | Владеет | Внешний контракт | Скрывает |
|---|---|---|---|
| Website | публичные страницы и собственная визуальная система | публичные URL, локальный `/api` только если необходим | компоненты, CSS и токены Website |
| Constructor | защищённые экраны поездок и собственная визуальная система | `/admin/**`, `/home`, существующие `/api/auth`, `/api/trips`, `/api/maps` | UI и предварительные вычисления |
| Interviews | защищённые исследования и собственная визуальная система | `/research/**`, существующие `/api/research` и `/api/auth` | UI, локальные стили и состояние экранов |
| Backend | домен, auth, данные и миграции | существующие `/api/**` | модели и бизнес-правила |
| Маршрутизатор | единый origin | маршруты выше, cookie и запросы без изменения семантики | расположение процессов и статика |

Тестовые швы: URL и браузерные сценарии каждого продукта, авторизованные API backend, настройки маршрутизатора, сборки и отсутствие межпродуктовых визуальных импортов.

## Ограничения

Бриф не требует создавать ещё не существующие функции или detail routes. Никаких платежей, новых бизнес-правил, внешних FX API и иных новых систем. Состояние Release и проверок показывать только по факту. При обнаружении необходимости изменения поведения, потери данных или существенной новой инфраструктуры — остановить затронутую часть и представить варианты.

## Детали исполнения и приёмки

- Инвентаризация фиксирует таблицу «маршрут или компонент / текущий файл / продукт / зависимости / Move, Keep или Archive» и отдельно неоднозначные принадлежности; исследуются маршруты, импорты, компоненты, CSS и переменные, дизайн-системы, API, базы и ORM, миграции, сессии, env, файлы, сборка, пакетный менеджер и CI/CD.
- До переноса проверяются ветка и status, сохранность пользовательских изменений и наличие экспериментов в архивируемом коммите; рабочая ветка и пользовательские изменения не перезаписываются, не прячутся и не сбрасываются. При чистой `main` создаётся `refactor/repository-architecture`; фактически исходная `master` была чистой основной веткой, а отдельная ветка создана от неё без изменения истории. Запрет reset --hard, force push, filter-repo, переписывания истории и уничтожения пользовательских данных сохраняется. Результат остаётся на ветке для review; автоматический merge в `main` не выполняется.
- Аннотированный тег `archive/legacy-test-pages-01-19` создан до удаления на проверенном коммите. Release с названием `Travel Club — Legacy Design Experiments (Test 01–19)` должен описывать версии, эксперименты, основные дизайнерские решения, выбранную основу и восстановление. Перед публикацией проверяются секреты и приватные данные. Пользователь запретил публикацию материалов CustDev: этот тег содержит такие материалы, поэтому публичная публикация этого снимка не допускается; сохраняется готовое локальное описание и тег. Сам факт существования общедоступной истории не снимает этот запрет.
- `/test_20` удаляется только после проверки действующих процессов и зависимостей; нужные ресурсы сохраняются, а исходный код остаётся восстановимым из истории Git. `/test_21`, если необходим для проверки, допускается исключительно как временный технический noindex alias. Удаляются лишь подтверждённо неиспользуемые компоненты, CSS, ресурсы и настройки; никаких ссылок на удалённые маршруты.
- Независимые Next.js-приложения и npm приняты по результатам изучения текущего стека при условии отсутствия чрезмерного риска. Каждое приложение имеет отдельные зависимости и конфигурацию; версии Next.js, React, TypeScript и прочих пакетов не обновляются ради реорганизации. Удаление зависимостей, конфигураций, импортов, ссылок и CSS допустимо только после проверки отсутствия использования.
- Секреты не переносятся и не публикуются; `.gitignore` проверяется, существующие env-переменные backend и подключение БД сохраняются. У каждого приложения свой `.env.example`, общие имена явно документируются. Локальные порты проверяются и документируются; будущая независимая доставка приложений должна быть возможной без изменения доменов сейчас.
- Обследовать и адаптировать существующий CI, если он есть; отдельные и общие проверки без лишней инфраструктуры. Если CI отсутствует, дать рекомендации и добавить минимальную конфигурацию только при необходимости. Не объединять ветку в main/master.
- Обновить корневой `README.md`, `docs/architecture/REPOSITORY_ARCHITECTURE.md`, `docs/archive/LEGACY_TEST_PAGES.md`, README каждого приложения. Описать продукты, директории, команды запуска и сборки каждого приложения и общие проверки, design systems, общие технические модули, API и пользователей, PostgreSQL, env, архив, назначение каждой версии, судьбу test_20 и test_21, восстановление и границы дальнейшего развития.
- Существующий `AGENTS.md` не переписывается без необходимости. Если для приложения нужны дополнительные локальные правила, добавить их отдельно, сохранив действующий проектный контракт.
- Последовательность: инвентаризация и зависимости → архитектура → архивирование → разделение → изоляция → подтверждённая очистка → документация и конфигурация → тестирование. Массовый перенос не начинается до установления зависимостей и прохождения проверки спецификации и плана.
- Проверить Website: `/`, `/formats`, `/archive`, `/start`, `/thanks`, прочие существующие страницы, ссылки и CTA, токены, Lato, загрузку шрифтов и изображений, формы и адаптивность. Уточнение про Lato относится ко всем страницам публичного Website, но не принуждает Constructor и Interviews менять их визуальную идентичность.
- Перенести утверждённые размеры текста, цвета, варианты логотипа и значения токенов Website; Pantone Cloud использовать после его окончательной фиксации, не выдумывая значение. Все три продукта используют свои собственные токены и визуальные ресурсы.
- Проверить Constructor: все действующие маршруты, создание/редактирование/сохранение поездки, календарь, карту, отдельные дни, API и PostgreSQL. Проверить Interviews: все маршруты, респондентов, сценарии и вопросы, проведение и сохранение ответов, результаты, версии и авторизацию. Для каждого приложения выполнить lint, typecheck, build, основные браузерные маршруты и консоль, API-ошибки, адаптивность; отдельно проверить импорты, ссылки, дубли, CSS-конфликты и отсутствие потери данных. Непроверенное явно обозначить.
- Итоговый отчёт содержит исходную и итоговую архитектуру, структуру и перемещения, архив и удалённые маршруты, тег и Release, дизайн-системы, общую логику, backend и БД, команды, результаты каждого вида проверки, ограничения и ручные действия; отдельная таблица сравнивает Website, Constructor и Interviews по независимому запуску, build, lint, typecheck, маршрутам, функциональности, CSS и дизайн-системе.

## Дополнение: общий Footer Website (G04–G38)

### Footer section 1 — Задача и решение

Сделать уже существующий общий Footer заметно компактнее и отделить его от содержимого страниц одной ясной navy-границей. Он остаётся частью единственного `SiteShell` и автоматически используется всеми существующими публичными маршрутами. Отдельный Footer, новые меню и новый бизнес-контент не создаются.

### Footer section 2 — Обязательное предварительное изучение

Перед изменениями осматриваются общий компонент Footer, его markup, стили, зависимости и положение после `main`; проверяются используемые Website-токены и отображение на разных публичных маршрутах. Главная страница используется как визуальный ориентир. `/formats` проверяется отдельно из-за общего светлого фона. Изменения реализации остаются в существующем SiteShell/Footer.

### Footer section 3 — Содержание и визуальная система

Сохраняются текущий логотип, подпись «Независимая редакция ваших путешествий», группы Navigation и Documents, все имеющиеся ссылки и копирайт. Navigation сохраняет пункты «Услуги», «О нас», «Архив», «Начать поездку». Documents сохраняет «Правовая информация», «Конфиденциальность», «Персональные данные» и другие уже существующие необходимые ссылки. Ссылки «О демонстрации» и уведомление о демонстрационной странице сохраняются только если текущая инвентаризация подтвердит, что они есть в Footer; любое описание такой страницы остаётся фактическим и не представляет услугу как завершённую. Текст ссылок и их направления не меняются; неподтверждённые контакты, социальные сети, юридические утверждения и новые пункты не добавляются. Удаляется только техническая надпись `DESIGN STUDY / 20`, если она присутствует.

По предварительной проверке текущей Website-системы `--tc-footer-bg` даёт светлый `--tc-paper`, `--tc-footer-line` ссылается на утверждённый navy `--tc-blue`, а общая геометрия задаётся `--tc-container-max: 1400px` и gutter-токенами в `apps/website/src/styles/travel-club-design-system.css`; это существующие значения, а не новые дизайн-решения. Footer сохраняет эти токены, шрифты и утверждённые текстовые роли Website. ASSUMPTION: тонкая граница в 1px соответствует существующей практике разделителей; это проверяется по текущим секциям, и при отличии берётся их принятая толщина. От границы до первого содержимого оставляется достаточный, но компактный интервал в рамках текущей шкалы отступов. Новые цвета, тени, карточки и декоративные рамки запрещены.

На стыке предыдущей секции и Footer видна ровно одна линия. Если у последней секции уже есть граница непосредственно на этом стыке, она остаётся единственной, а дополнительная граница Footer для этого случая не отображается. Существующие внутренние линии секции, разделяющие её собственные материалы, не считаются линией на стыке. Содержимое и вертикальные отступы самой предыдущей секции не сокращаются ради компактности Footer.

### Footer section 4 — Компактность и адаптивность

Высота Footer измеряется одним и тем же способом до и после при ширине 1280px на `/`, `/formats` и `/services/route`. Выбор viewport 1280px и `getBoundingClientRect().height` — ASSUMPTION для воспроизводимого замера в пределах запрошенных desktop-ширин; замер 452.78px — только зафиксированное исходное наблюдение, не отдельное требование. Целевой результат — ориентировочно на 25–35% ниже исходного; сокращение достигается главным образом верхними и нижними полями, внутренними промежутками, интервалами групп и нижней строкой. Шрифты и текстовые роли не уменьшаются ради цели; читаемость важнее точного процента.

На desktop сохраняются три колонки в таком порядке: Brand слева, Navigation в центре, Documents справа. На tablet сетка перераспределяется без тесных или неудобных переносов. На mobile допускаются две колонки либо вертикальное расположение, при этом Brand остаётся первым, затем Navigation и Documents; проверяется отсутствие чрезмерного свободного пространства после последней ссылки и между группами. ASSUMPTION — для touch-ширин зоны ссылок и «Наверх» имеют не менее 44px высоты как конкретное прочтение требования «удобные области нажатия». Обычные desktop-ссылки остаются компактными. Ни на одной требуемой ширине документ не должен расширяться за viewport.

### Footer section 5 — Проверка и отчёт

- Предварительная карта Website-маршрутов по текущим route-файлам и README — `/`, `/formats`, `/archive`, `/start`, `/thanks`, `/legal`, `/privacy`, `/personal-data`, `/payment`, `/services/route`, `/services/turnkey`, `/tours` и not-found; перед приёмкой сверить её с фактической инвентаризацией. После изменений открыть в браузере каждый фактически существующий публичный маршрут и проверить, что там используется ровно один Footer. `/archive/[slug]` и `/tours/[slug]` — ожидаемые для проверки detail routes, но их отсутствие подтвердить по инвентаризации и не создавать.
- Навигационные и документные ссылки ведут на существующие маршруты или назначенные якоря. Текущий `SiteShell` задаёт верхнюю цель `#top`, а Footer уже использует её в ссылке «Наверх»; сохранить проверенную цель после осмотра текущего кода. Как нативная ссылка, контроль доступен клавиатуре; проверить видимый фокус и стандартную активацию.
- Проверяются светлые и тёмные последние секции, в том числе `/formats`, на которой граница не удваивается.
- Для всех пяти ширин — 375, 430, 768, 1280 и 1440px — проверяются переполнение и макет; для трёх меньших проверяется мобильная/планшетная компоновка.
- Сравнительные viewport-скриншоты с видимым окончанием предыдущей секции и Footer снимаются при 1280px до и после на `/`, `/formats` и `/services/route`. Выбор `/services/route` как представительной сервисной страницы — принятое за пользователя допущение; маршрут используется только для сравнения компоновки Footer, не как заявление о завершённости услуги.
- Выполняются Website lint, typecheck и production build. Поведение общего Footer проверяется на существующих E2E/unit seams; тесты не меняют пользовательский контент.
- Итоговый отчёт перечисляет изменённые файлы, исходную и итоговую высоту Footer с процентом сокращения, выбранный способ разделения с предыдущей секцией и защиту от двойной линии, мобильную компоновку и выполненные проверки. К отчёту приложены сравнительные скриншоты из предыдущего пункта.

### Footer section 6 — Границы

Не меняются Header, основные секции страниц, токены и значения палитры, Lato и размеры текстовых ролей, логотип, контент услуг и навигационная структура, backend, формы, Constructor и Interview Platform. Правки ограничены общим Footer, его непосредственной границей и тестами этого Footer.
