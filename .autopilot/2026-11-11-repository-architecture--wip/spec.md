# Спецификация: разделение репозитория

## Результат и границы

Три самостоятельных Next.js-приложения npm в `apps/website`, `apps/trip-constructor`, `apps/interviews`; каждое владеет собственными маршрутами, настройками, CSS, шрифтами, визуальными компонентами, ресурсами и тестами. Никаких межпродуктовых визуальных импортов. Нейтральный общий код допускается только при подтверждённой потребности. Существующий FastAPI, PostgreSQL, модели, миграции, авторизация и формулы остаются едиными источниками истины.

## Контракт поведения

1. Website сохраняет все существующие публичные маршруты и `/` из test_21, переименованные компоненты, активные изображения и IndexedDB редактора; не создаёт отсутствующих detail routes. `/test_21` удаляется либо остаётся только noindex. Все публичные страницы используют утверждённую систему, включая Lato; это уточнение пользователя допускает соответствующее изменение типографики старых страниц. Не выдумывать новый Pantone Cloud.
2. Constructor сохраняет `/admin/**`, клиентский просмотр, создание, редактирование, календарь, карту, шаги и расчёты; Interviews сохраняет `/research/**`, анкеты, сценарии, ответы, версии, экспорт и защиту admin. `/home` — защищённый общий каталог, очищенный от архивных ссылок; его место выбирается так, чтобы существующие ссылки на едином адресе работали. Поведение и данные не переписываются.
3. На общем origin входящие `/research/**` направляются Interviews, `/admin/**` и `/home` — Constructor, остальные публичные маршруты — Website; `/api/**` идёт в имеющийся backend. Прокси сохраняет методы, тела, заголовки и host-only cookie. Для локального самостоятельного запуска каждый private frontend имеет работающий путь к backend и входу без запуска двух других. Разные статические ресурсы Next и `public/` должны быть адресованы без конфликтов. Не вводить внешний домен и не объявлять production deployment выполненным.
4. Старые `/test` (исторический первый эксперимент), `/test_2`…`/test_20` архивируются тегом до удаления. Сохраняются живые зависимости, например изображения из `public/test_20`, пока они используются, с нормальными именами в собственном приложении. Архивная документация раскрывает фактическое отсутствие `/test_1` и историю версий. GitHub Release готовится по проверенному содержимому без раскрытия чувствительной информации. История Git не переписывается, чужие изменения не стираются.
5. Три набора корневых глобальных стилей и дизайн-систем независимы. Constructor и Interviews сохраняют внешний вид; временное изменение токена каждого приложения с проверкой остальных и обязательным восстановлением демонстрирует изоляцию. На Website адаптер всех страниц использует утверждённые токены и локальные Lato-файлы.
6. Корневые npm-команды запускают, собирают и проверяют приложения по отдельности и все вместе. Зафиксированы доступные порты, `.env.example` каждого приложения и происхождение общих backend-переменных. Запуск одного frontend не требует запуска остальных; backend требуется только там, где требуется существующая функциональность.
7. Исходная карта, архитектура, восстановление из тега, runbooks и README приложений документируют фактическое состояние, ограничения и маршрутизацию. Существующая конфигурация развёртывания не меняет публичный домен или данные; отсутствие CI не оправдывает сложную новую инфраструктуру.
8. Приёмка включает lint/typecheck/build и тесты каждого приложения, все основные маршруты, авторизацию, браузерную консоль и запросы, адаптивность, ссылки и ресурсы, бизнес-сценарии Constructor и Interviews, API/БД, CSS-изоляцию и регрессии. Любую недоступную проверку назвать, не представлять как пройденную. Базы не очищать, пользовательские данные не удалять.

## Границы и швы

| Единица | Владеет | Внешний контракт | Скрывает |
|---|---|---|---|
| Website | публичные страницы и собственная визуальная система | публичные URL, локальный `/api` только если необходим | компоненты, CSS и токены Website |
| Constructor | защищённые экраны поездок и собственная визуальная система | `/admin/**`, `/home`, существующие `/api/auth`, `/api/trips`, `/api/maps` | UI и предварительные вычисления |
| Interviews | защищённые исследования и собственная визуальная система | `/research/**`, существующие `/api/research` и `/api/auth` | UI, локальные стили и состояние экранов |
| Backend | домен, auth, данные и миграции | существующие `/api/**` | модели и бизнес-правила |
| Маршрутизатор | единый origin | маршруты выше, cookie и запросы без изменения семантики | расположение процессов и статика |

Тестовые швы: URL и браузерные сценарии каждого продукта, авторизованные API backend, настройки маршрутизатора, сборки и отсутствие межпродуктовых визуальных импортов.

## Ограничения

Бриф не требует создавать ещё не существующие функции или detail routes. Никаких платежей, новых бизнес-правил, внешних FX API и иных новых систем. Состояние Release и проверок показывать только по факту. При обнаружении необходимости изменения поведения, потери данных или существенной новой инфраструктуры — остановить затронутую часть и представить варианты.

## Детали исполнения и приёмки

- Инвентаризация фиксирует таблицу «маршрут или компонент / текущий файл / продукт / зависимости / Move, Keep или Archive» и отдельно неоднозначные принадлежности; исследуются маршруты, импорты, компоненты, CSS и переменные, дизайн-системы, API, базы и ORM, миграции, сессии, env, файлы, сборка, пакетный менеджер и CI/CD.
- До переноса проверяются ветка и status, сохранность пользовательских изменений и наличие экспериментов в архивируемом коммите; рабочая ветка и пользовательские изменения не перезаписываются, не прячутся и не сбрасываются. При чистой `main` создаётся `refactor/repository-architecture`; фактически исходная `master` была чистой основной веткой, а отдельная ветка создана от неё без изменения истории. Запрет reset --hard, force push, filter-repo, переписывания истории и уничтожения пользовательских данных сохраняется.
- Аннотированный тег `archive/legacy-test-pages-01-19` создан до удаления на проверенном коммите. Release с названием `Travel Club — Legacy Design Experiments (Test 01–19)` должен описывать версии, эксперименты, основные дизайнерские решения, выбранную основу и восстановление. Перед публикацией проверяются секреты и приватные данные. Пользователь запретил публикацию материалов CustDev: этот тег содержит такие материалы, поэтому публичная публикация этого снимка не допускается; сохраняется готовое локальное описание и тег. Сам факт существования общедоступной истории не снимает этот запрет.
- `/test_20` удаляется только после проверки действующих процессов и зависимостей; нужные ресурсы сохраняются. `/test_21`, если необходим для проверки, допускается исключительно как временный технический noindex alias. Удаляются лишь подтверждённо неиспользуемые компоненты, CSS, ресурсы и настройки; никаких ссылок на удалённые маршруты.
- Независимые Next.js-приложения и npm приняты по результатам изучения текущего стека при условии отсутствия чрезмерного риска. Каждое приложение имеет отдельные зависимости и конфигурацию; версии Next.js, React, TypeScript и прочих пакетов не обновляются ради реорганизации. Удаление зависимостей, конфигураций, импортов, ссылок и CSS допустимо только после проверки отсутствия использования.
- Секреты не переносятся и не публикуются; `.gitignore` проверяется, существующие env-переменные backend и подключение БД сохраняются. У каждого приложения свой `.env.example`, общие имена явно документируются. Локальные порты проверяются и документируются; будущая независимая доставка приложений должна быть возможной без изменения доменов сейчас.
- Обследовать и адаптировать существующий CI, если он есть; отдельные и общие проверки без лишней инфраструктуры. Если CI отсутствует, дать рекомендации и добавить минимальную конфигурацию только при необходимости. Не объединять ветку в main/master.
- Обновить корневой `README.md`, `docs/architecture/REPOSITORY_ARCHITECTURE.md`, `docs/archive/LEGACY_TEST_PAGES.md`, README каждого приложения. Описать продукты, директории, команды запуска и сборки каждого приложения и общие проверки, design systems, общие технические модули, API и пользователей, PostgreSQL, env, архив, назначение каждой версии, судьбу test_20 и test_21, восстановление и границы дальнейшего развития.
- Последовательность: инвентаризация и зависимости → архитектура → архивирование → разделение → изоляция → подтверждённая очистка → документация и конфигурация → тестирование. Массовый перенос не начинается до установления зависимостей и прохождения проверки спецификации и плана.
- Проверить Website: `/`, `/formats`, `/archive`, `/start`, `/thanks`, прочие существующие страницы, ссылки и CTA, токены, Lato, загрузку шрифтов и изображений, формы и адаптивность. Уточнение про Lato относится ко всем страницам публичного Website, но не принуждает Constructor и Interviews менять их визуальную идентичность.
- Перенести утверждённые размеры текста, цвета, варианты логотипа и значения токенов Website; Pantone Cloud использовать после его окончательной фиксации, не выдумывая значение. Все три продукта используют свои собственные токены и визуальные ресурсы.
- Проверить Constructor: все действующие маршруты, создание/редактирование/сохранение поездки, календарь, карту, отдельные дни, API и PostgreSQL. Проверить Interviews: все маршруты, респондентов, сценарии и вопросы, проведение и сохранение ответов, результаты, версии и авторизацию. Для каждого приложения выполнить lint, typecheck, build, основные браузерные маршруты и консоль, API-ошибки, адаптивность; отдельно проверить импорты, ссылки, дубли, CSS-конфликты и отсутствие потери данных. Непроверенное явно обозначить.
- Итоговый отчёт содержит исходную и итоговую архитектуру, структуру и перемещения, архив и удалённые маршруты, тег и Release, дизайн-системы, общую логику, backend и БД, команды, результаты каждого вида проверки, ограничения и ручные действия; отдельная таблица сравнивает Website, Constructor и Interviews по независимому запуску, build, lint, typecheck, маршрутам, функциональности, CSS и дизайн-системе.
