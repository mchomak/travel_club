\# ЗАДАЧА: ПОЛНАЯ АРХИТЕКТУРНАЯ РЕОРГАНИЗАЦИЯ REPOSITORY TRAVEL CLUB\
\
\## 1. Цель проекта\
\
Необходимо провести архитектурную реорганизацию текущего репозитория Travel Club.\
\
Сейчас в одном проекте находятся три самостоятельных продукта, несколько поколений экспериментальных страниц, общие стили и компоненты, а также различные технические реализации.\
\
Наша задача — превратить репозиторий в чистую, понятную и масштабируемую архитектуру, в которой три продукта существуют независимо друг от друга.\
\
\*\*Целевая архитектура:\*\*\
\
1\. Travel Club Website — основной публичный сайт компании.\
2\. Trip Constructor — приложение для создания и планирования путешествий.\
3\. Interview Platform — внутренняя платформа для проведения интервью и исследований.\
\
Мы хотим сохранить один GitHub-репозиторий, но разделить его на три независимо развиваемых и собираемых приложения (Monorepo).\
\
Каждое приложение должно иметь:\
\- Собственную структуру страниц и маршрутов.\
\- Собственные компоненты.\
\- Собственную дизайн-систему.\
\- Собственные CSS-файлы и глобальные стили.\
\- Собственные настройки приложения.\
\- Возможность независимого запуска и сборки.\
\
Общими могут оставаться только действительно необходимые технические модули: типы данных, утилиты, API-клиенты и другая нейтральная инфраструктура.\
\
\*\*Визуальные компоненты, дизайн-токены, шрифты и стили между тремя продуктами не объединяем.\*\*\
\
Главный принцип: изменение дизайна или архитектуры одного приложения не должно неожиданно влиять на два других.\

\# 3. Git и безопасное начало работы\
\
Перед реорганизацией:\
\
1\. Проверь текущую ветку.\
2\. Проверь \`git status\`.\
3\. Убедись, что все необходимые изменения сохранены.\
4\. Проверь, нет ли незакоммиченных пользовательских изменений.\
\
Если рабочая директория чистая и текущая ветка — \`main\`, создай отдельную ветку:\
\
\`refactor/repository-architecture\`\
\
Если уже используется рабочая ветка, не перезаписывай её.\
\
Если обнаружены незакоммиченные изменения, не удаляй, не сбрасывай и не прячь их автоматически. Сначала оцени возможность безопасного продолжения. Не включай чужие изменения в архивные коммиты.\
\
Не выполняй:\
\- \`git reset --hard\`.\
\- Force push.\
\- Переписывание истории Git.\
\- Удаление старых коммитов.\
\- Очистку Git History через filter-repo.\
\- Принудительное удаление пользовательских файлов.\
\
Все изменения должны оставаться обратимыми.\

\# 4. Архивирование старых тестовых страниц\
\
Это отдельная обязательная часть задачи.\
\
В основной ветке больше не должны находиться ненужные экспериментальные страницы \`test_1\`–\`test_19\`.\
\
Однако перед удалением необходимо сохранить возможность вернуться к этим версиям.\
\
\### 4.1. Создание архивной точки\
\
До удаления страниц:\
\
1\. Убедись, что текущий Git-коммит содержит все необходимые экспериментальные страницы.\
2\. Создай аннотированный Git Tag:\
\
\`archive/legacy-test-pages-01-19\`\
\
3\. Подготовь GitHub Release:\
\
\*\*Название:\*\* Travel Club — Legacy Design Experiments (Test 01–19).\
\
В описании укажи:\
\- Что представляют собой архивные версии.\
\- Какие эксперименты проводились.\
\- Какие основные дизайнерские решения проверялись.\
\- Какая версия стала основой дальнейшей разработки.\
\- Как восстановить исходный код нужной страницы из тега.\
\
Перед публикацией Release проверь репозиторий на наличие случайно сохранённых секретов, ключей API, паролей и приватных данных. Не публикуй чувствительные материалы. Если создание Release невозможно из-за отсутствия GitHub-доступа, создай локальный тег и подготовь готовое описание Release.\
\
Не переписывай историю Git.\
\
\### 4.2. Судьба test_20\
\
\`/test_20\` — предыдущая экспериментальная версия с интерактивной панелью Design Settings.\
\
Проверь, используется ли она ещё в каких-либо действующих процессах.\
\
Поскольку утверждённая дизайн-система уже создана, а \`/test_21\` использует централизованные токены, панель настройки больше не должна быть частью публичного сайта.\
\
Если \`/test_20\` больше не нужна:\
\- Сохрани её исходный код в архивной Git-истории.\
\- Удали её активный маршрут.\
\- Не удаляй компоненты и ресурсы, которые используются другими приложениями.\
\
Если обнаружится действующая зависимость, не удаляй её автоматически — укажи причину.\
\
\### 4.3. Судьба test_21\
\
Реализация \`/test_21\` является основой основного публичного сайта.\
\
Не рассматривай её как устаревшую тестовую страницу.\
\
Её компоненты и содержание должны получить нормальные production-названия и использоваться в приложении \`website\`.\
\
Главный публичный маршрут — \`/\`.\
\
Самостоятельный маршрут \`/test_21\` не должен оставаться второй индексируемой копией главной. Если он временно необходим для проверки, оставь его только как технический alias с соответствующими ограничениями индексации.\
\
\### 4.4. Очистка\
\
После успешного архивирования и проверки зависимостей:\
\
\- Удали активные маршруты \`test_1\`–\`test_19\`.\
\- Удали уникальные компоненты этих страниц, если они больше нигде не используются.\
\- Удали неиспользуемые CSS-файлы и стили.\
\- Удали неиспользуемые изображения и ресурсы, если они относятся только к удалённым экспериментам.\
\- Удали неиспользуемые настройки тестовых страниц.\
\
Не удаляй общие ресурсы, даже если они первоначально появились в одной из тестовых версий.\
\
Не оставляй неиспользуемые копии компонентов и тестовые маршруты под другими названиями.\

\# 6. Полная изоляция дизайн-систем\
\
Это одно из главных требований всей реорганизации.\
\
Каждый продукт должен иметь собственную независимую визуальную систему.\
\
\### 6.1. Website Design System\
\
Основной сайт использует уже утверждённую дизайн-систему:\
\
\- Основной шрифт — Lato.\
\- Утверждённые размеры текста.\
\- Утверждённые цвета и Pantone Cloud после его окончательной фиксации.\
\- Утверждённые варианты логотипа.\
\- Собственные типографические токены.\
\- Собственные цветовые темы.\
\- Собственные компоненты.\
\- Собственные глобальные стили.\
\
Существующая дизайн-система Website должна быть перенесена без потери утверждённых значений.\
\
Не придумывай новые визуальные решения.\
\
\### 6.2. Constructor Design System\
\
Конструктор получает собственную дизайн-систему.\
\
Не копируй туда автоматически цвета, шрифты, размеры и компоненты основного сайта.\
\
Сохрани существующее утверждённое оформление конструктора.\
\
В дальнейшем оно должно изменяться независимо от Website.\
\
\### 6.3. Interview Design System\
\
Платформа интервью также получает собственную дизайн-систему.\
\
Не заставляй её использовать Lato, палитру Website или визуальные компоненты конструктора.\
\
Сохрани её текущую функциональность и визуальную идентичность.\
\
\### 6.4. Запрет на общие визуальные зависимости\
\
Не создавай общий пакет:\
\
\- \`shared-ui\`.\
\- \`shared-design-system\`.\
\- \`global-tokens\`.\
\- \`shared-theme\`.\
\
Не подключай одну общую таблицу CSS Variables ко всем приложениям.\
\
Не импортируй кнопки, карточки, формы и другие визуальные компоненты из одного приложения в другое.\
\
Даже если два приложения используют похожие элементы, их визуальные реализации должны оставаться независимыми.\
\
Разрешается разделять:\
\- Типы данных.\
\- Нейтральные утилиты.\
\- API-клиенты.\
\- Схемы валидации.\
\- Технические функции.\
\- Общие бизнес-правила, если они действительно совпадают.\
\
\### 6.5. Проверка изоляции\
\
После разделения обязательно проведи проверку:\
\
1\. Измени временно тестовый цветовой токен Constructor.\
2\. Убедись, что Website визуально не изменился.\
3\. Убедись, что Interview Platform не изменилась.\
4\. Проверь обратную независимость остальных приложений.\
\
Тестовый токен после проверки верни к исходному значению.\

\# 7. Backend, API и база данных\
\
Необходимо сохранить существующую бизнес-логику и инфраструктуру.\
\
Перед перемещением изучи:\
\
\- Где находятся API-обработчики.\
\- Какие приложения используют одни и те же API.\
\- Как организована авторизация.\
\- Как работает доступ к базе данных.\
\- Где хранятся схемы и миграции.\
\- Как обрабатываются файлы.\
\- Какие переменные окружения используются.\
\
\*\*Не разделяй базу данных на три отдельные базы только ради визуального разделения приложений.\*\*\
\
Если приложения используют общую базу, сохрани существующую модель данных.\
\
Если backend общий:\
\- Сохрани единый источник бизнес-логики.\
\- Не дублируй обработчики запросов.\
\- Не ломай существующие API-контракты.\
\- Документируй, какие приложения используют каждый API.\
\
Если backend находится внутри одного Next.js-приложения и используется другими продуктами, сначала определи безопасный способ его отделения или сохранения.\
\
Не создавай новый backend и не переписывай API без необходимости.\
\
Все миграции базы данных должны остаться доступными и иметь один контролируемый источник истины.\
