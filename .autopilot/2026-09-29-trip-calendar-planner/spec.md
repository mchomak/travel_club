# Спецификация: календарь конструктора поездок

## Задача

Администратор составляет тур по дням, но текущий список плохо показывает, чем занят каждый час и сколько времени остаётся. Особенно трудно оценить ночной перелёт и размещение в отеле, а на iPad нужно выполнять те же действия без неудобной настольной компоновки.

## Решение

Основная часть конструктора станет календарём с часовой сеткой и датами тура. События займут свои интервалы, включая части двух соседних дней. Над сеткой пройдут полосы проживания в отелях; заезд и выезд будут отмечены в точные часы. В шапке останется короткая информация о туре, под календарём — явные кнопки добавления. Нажатие на событие откроет боковую панель редактирования. Для каждого дня можно задать статус. Каждому пункту маршрута можно приложить ссылку.

## Решения по реализации

1. Существующий FastAPI/SQLAlchemy/PostgreSQL и Next/React остаются. Итерируем текущие TripInput, API и формы, потому что существующие авторизация, черновик и расчёт уже работают.
2. У дня добавляется необязательная строка `status`. У пункта добавляются необязательные `end_day_id`, `check_in_time`, `check_out_time`, `external_url`. `day_id` остаётся днём начала; `end_day_id` связывается с днём того же тура. Старая запись без новых полей читается без ручной правки.
3. Форма показывает дату окончания события через список дней тура; API проверяет принадлежность обоих дней поездке и хронологию дат/времени. Если конец не задан, обычный интервал остаётся в пределах первого дня; старое `end_time < start_time` трактуется как следующий день при отображении. Местные настенные часы показываются без часовых поясов и арифметического пересчёта; для перелётов это визуальная схема занятости, а не доказательство физической длительности полёта.
4. Проживание — существующий пункт `hotel`: даты и часы регистрации живут в нём, полоса и два маркера вычисляются из одной записи. Оплата номеров продолжает рассчитываться по ночам от заезда до выезда согласно текущему ADR; дата выезда может быть первым днём за пределами тура, тогда полоса обрезается по краю календаря, а дата/время выезда видны в редакторе и подписи полосы.
5. Сетка строится из дат тура и локальных строк HH:MM. На широком экране неделя, на планшете три дня, на телефоне один день с явным переключением. Высота часа постоянна, доступна вертикальная прокрутка; событие, пересекающее границу отрезка, рисуется по видимой части. Параллельные события делят ширину колонки.
6. Цвета привязаны к типу пункта; тёмная календарная поверхность следует образцу пользователя. Внешние формы и финансы остаются в целостной палитре и адаптируются. Для доступности карточки являются кнопками с текстом, фокусом и клавиатурным открытием; цвет не единственный носитель смысла.
7. Боковая панель использует текущую форму пункта и существующие действия сохранения/удаления. Список пунктов без валидного времени и общих затрат размещается после календаря. Верхний блок содержит только краткие поля и навигацию; добавление пунктов следует за календарём.
8. URL валидируется в API и в форме. В закрытом интерфейсе открытие получает `target=_blank` и `rel=noopener noreferrer`; новые административные поля не расширяют клиентский Preview DTO. Изменение DTO и БД выполняется аддитивной Alembic-миграцией.
9. Сохранение всей поездки, версия, авторизация, финансовые расчёты и удаление дат продолжают идти через существующие интерфейсы. При подтверждённом сокращении удаляются пункты, которые ссылаются на удалённый конечный день; до подтверждения возврат ошибки не меняет сохранённую запись.

## Границы и швы

| Модуль | Владеет | Выставляет | Прячет |
|---|---|---|---|
| API поездок | Проверка и сохранение TripInput, восстановление/дублирование, контроль дат | Существующие CRUD, calculate и preview контракты с расширенными необязательными полями дня/пункта | Транзакции, связи по одному туру, подтверждение удаления |
| Расписание календаря | Преобразование дней и пунктов в видимые отрезки, полосы и маркеры | `buildCalendarEntries(days, items, visibleDates)` с позициями и типами записей | Деление через полночь, обрезку, разбор местных часов, размещение пересечений |
| Редактор поездки | Выбор даты, статус дня, открытие/сохранение пунктов, responsive-компоновка | Существующий TripInput/действия редактора и callback открытия пункта по id | Черновик, модальное/боковое представление, визуальное состояние |
| Расчёт стоимости | Прежняя финансовая модель | Существующие `calculate_trip(TripInput)` и клиентский предварительный расчёт | Decimal-формулы и распределение ночей |

Проверочные швы: API `TripInput` через существующие маршруты и чистая функция `buildCalendarEntries`; расчёт проверяется существующими публичными функциями. Визуальные действия проверяются через закрытую страницу редактора.

## Вне рамок

Нет отложенных требований. Пересчёт часовых поясов не запрошен и прямо отклонён ответом пользователя; автоматические бронирования и внешние календарные интеграции не входят в задачу R01/R16.

## Открытые места

Нет. Допущение для R03: визуальная длительность между местными часами используется только для планирования календаря; реальное полётное время по часовым поясам не вычисляется. Допущение для R14: если удалённой ветки `main` ещё нет, создаём её из текущей локальной истории обычным push без force.
