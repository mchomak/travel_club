# Спецификация: пошаговый конструктор Travel Club

## Задача и решение

Пользователь создаёт одну поездку в шесть этапов и планирует каждый день, видя общий календарь над подробным редактором. Полный редактор остаётся доступен по прежнему адресу. Модели маршрута, формы, расчёт и механизм хранения переиспользуются; независимых копий состояния нет.

## Самобрифинг

- ASSUMPTION: новый адрес `/admin/trips/[id]/builder`; существующий `/admin/trips/[id]` сохраняется. Создание направляет в builder; из обоих режимов можно перейти в другой после подтверждённого сохранения.
- ASSUMPTION: отдельный согласованный макет не приложен. Используем текстовую композицию из брифа и текущий визуальный язык admin, без редизайна сайта.
- ASSUMPTION: этап и выбранный день — параметры URL, а не вторая модель поездки. Возобновление по URL восстанавливает этап/день; бизнес-данные всегда читаются из API.
- Для новых перелётов с разными часовыми поясами вводятся явные UTC-смещения на даты отправления и прибытия. Автоматического определения IANA/DST не добавляем. Старые записи с null сохраняют текущие правила местного времени.
- Пользовательские данные и рабочая PostgreSQL не очищаются. Проверки используют отдельную тестовую БД или только записи, созданные прогоном.

## §1 Аудит и сохранение совместимости

Перед реализацией записать audit.md: создание, календарь, категории форм, API/БД, география, начало/конец дня, маршрутизация, финансовые формулы, CRUD, зависимости и повторное использование. Не менять несвязанные публичные страницы. `TripEditor` и `DraftSession` — единая точка редактирования; новый режим компонуется вокруг тех же handlers/modal forms. Сохраняем полные возможности старого режима, аутентификацию, CSRF, optimistic version, клиентский allowlist, дату удаления с подтверждением. Любая новая схема — nullable additive migration с сохранением старых данных.

## §2 Создание и навигация этапов

1. Основные параметры: существующий TripForm в basic-варианте показывает название, начало/окончание, участников и валюту. Статус нового документа всегда draft. Дополнительные поля доступны через раскрываемые дополнительные параметры или после создания в параметрах; не исчезают из полного редактора. Серверное создание выполняется однократно, submit блокируется на запросе; ошибка оставляет ввод.
2. Перелёты и дальние переезды: существующий ItemForm для flight/train_bus/дальнего транспорта, общие списки и редактирование/удаление. Локальные taxi/walk в этом этапе не предлагаются, но доступны в дне. Сохраняются все существующие поля, точки, местные дата/время, стоимость, ссылки/заметки, аэропортовые блоки. Добавление сразу видно в общем календаре, без копий.
3. Проживание: существующая hotel-форма и список любого числа отелей, все доступные поля, даты/время check-in/out, комнаты/стоимость/точки/ссылки/заметки. Без интерактивной карты на экране этапа (location inputs допускаются без canvas). Отели выводятся тем же календарём.
4. Программа по дням — §3.
5. Дополнительные расходы и стоимость: существующие expense categories и Finances/RatesForm, все расчётные режимы, FX, себестоимость, наценка/target margin, клиентская цена, прибыль. Существующие расходы событий включаются автоматически; денег через Number не считать.
6. Проверка: сводка дат, участников, элементов, расходов и стоимости; предупреждения о пустых днях, интервалах/конфликтах времени, ночёвках, отсутствующих точках/неоднозначных границах, неизвестных ценах/курсах. Ссылки на проблемный день/элемент. Предупреждения не блокируют сохранение черновика или завершение; серверные ошибки валидации не игнорируются. Завершение ожидает session.save() и переводит в полный редактор, без принудительного статуса ready.

Любой этап можно открыть напрямую после создания, пропустить или вернуться назад. Этапы и дни меняют только представление в одном mounted Editor с тем же DraftSession, без refetch/remount. Применённые изменения сохраняются асинхронно существующей очередью; незавершённый modal form нельзя молча закрыть переключением. Переходы на другой route/preview/full editor ожидают актуальный flush; при ошибке остаются здесь с возможностью повтора. Быстрые переходы не теряют ввод. Dirty/dates-shrink/conflict guards действуют в обоих режимах.

## §3 Программа по дням

Порядок: шапка → полный существующий TripCalendar → горизонтальная навигация дней с предыдущим/следующим → три колонки → переходы к дню/этапам. Шапка содержит название/даты/участников/этап, параметры, preview, save и подтверждённый статус.

- Общий календарь сохраняет тёмно-синий стиль, все дни/отели/перелёты/события, пагинацию/горизонтальный скролл, редактирование, выбор интервала и drag/move. Выбор дня управляет нижним редактором. Существующие события открываются той же формой.
- Левая колонка — тот же TripCalendar с optional visibleDayId, которому по-прежнему передаётся ПОЛНЫЙ массив days для корректных end_day_id и ночных интервалов. Ограничивается только отображение, не модель. Заголовок и доступное имя отличают от общего календаря.
- Центр — последовательный список всех элементов, относящихся к выбранному дню, включая прибытия/ночные сегменты/проживание и без времени. Один item ID показывается один раз в списке. Время, название, адрес, продолжительность (для зон — фактическая), действия редактирования/удаления/переноса. Прежние кнопки Перелёт, Транспорт, Проживание, Еда, Впечатления. Начало и конец дня с auto/manual — существующая Boundary логика, вынесенная без дублирования. Доступна DayForm и заметки дня.
- Справа — существующая интерактивная карта точек выбранного дня с нумерацией, геометрией, логистикой/маршрутными расчётами и явным добавлением transfer; под ней дневная стоимость из `calculation.days`, не сумма полных item totals. При отсутствии настроек карты/сети показывается существующее понятное сообщение и текстовый маршрут; остальные операции доступны.
- Желательная связанная подсветка: optional selectedItemId/onSelectItem у календаря/списка/карты; щелчок существующего события сохраняет прежнее открытие формы и синхронизирует выделение. Не менять бизнес-данные ради подсветки.
- Большой экран: три колонки с разумными min-width, календарь прокручивается. Планшет: две колонки/карта ниже или переключаемая; узкий экран: последовательные блоки без искусственного сжатия. Все действия доступны с клавиатуры, focus/labels/aria-current, явные empty/loading/error states.

## §4 Автоматический каркас и границы дней

Автоматическое формирование — derived read model поверх trip.items и buildCalendarEntries/buildDayRoute, никаких новых сохраняемых копий и фиктивных переездов. Flight/hotel, добавленные на ранних этапах, сразу участвуют в дне. Hotel: начало дня от предыдущей ночи (`check_in < date <= check_out`), конец — следующая ночь (`check_in <= date < check_out`). День checkout не считается следующей ночёвкой. Несколько кандидатов требуют ручного выбора, не произвольного первого.

Учитываем первый/последний день, смену отеля, отсутствие проживания, ночные события/переезды, включая промежуточный день многодневного переезда. Ночной транспорт может заменять ночёвку; не выдавать фиктивную пропущенную ночь во время транзита и не возвращать неверно к отелю. Ручные map_start/map_end имеют приоритет, сохраняются в БД и не затираются derived вычислениями. Изменение/удаление источника немедленно пересчитывает derived представление, без дублей. Старые явно созданные transfers сохраняются как реальные items и не удаляются автоматически.

## §5 Часовые пояса и календарное время

Минимальное расширение item: nullable `departure_utc_offset_minutes`/`arrival_utc_offset_minutes`, целые в [-840,840], либо оба, либо ни одного, только для scheduled transport. UTC instant = local date/time minus offset. Проверяем положительную фактическую длительность при обеих датах/временах. Для заданных offsets и null end_day_id дата прибытия равна local departure date; legacy next-day inference только без offsets. Разрешены прибытие раньше по местным часам и на предыдущую местную дату при положительном UTC-интервале. Запрещаем неполную пару, неверный диапазон/хронологию явно и в форме, и на сервере.

Календарь остаётся местным: не сдвигает точки по UTC, не скрывает корректный flight с обратным местным интервалом, показывает раздельные departure/arrival сегменты/маркеры там, где обычный сплошной интервал ложен. Drag сохраняет UTC-длительность и переносит arrival с его смещением. Airport blocks якорятся на соответствующий локальный endpoint. Все новые поля проходят create/save/reload/duplicate; null у старых записей не меняет вид/расписание. Не заявляем автоматическое DST: UI объясняет ввод смещений на дату события.

## §6 Надёжное сохранение и финансы

Один DraftSession на поездку, один aggregate и тот же REST. Existing serialized flush с revision checks и optimistic version переиспользуется; усилить только найденные races. «Сохранено» только после ответа сервера на последнюю revision; pending form не маскируется сохранённым документом. Network failure сохраняет local draft и доступный retry. При потерянном ответе/409 нельзя молча overwrite: понятное сообщение, сохранение черновика и явный reload с подтверждением. Не создаём дубликаты при повторном save; полная PUT aggregate с устойчивыми UUID. Нет бесконечного авто-retry.

Decimal/backend pricing неизменен. И дневной summary, и общий календарь используют day allocation из Calculation.days (в том числе hotel/multi-day), так что сумма дней + general = trip total. После изменения участников/дат/курсов/элементов authoritative save возвращает новую смету; при отсутствии FX показываем ошибку вместо ложной суммы. Preview получает данные только после save и использует прежний безопасный endpoint.

## §7 Проверки и приёмка

Автоматизированный полный сценарий 7–8 дней: create draft → несколько long-haul → два отеля с разными датами → derived calendar/day → все категории дня → переходы туда/обратно → edit через оба календаря и item list → точки/карта/boundary → save/reload → чтение настоящей PostgreSQL → move/delete/no duplicates → пересчёт → старый editor → network error/retry/rapid changes → tablet/desktop.

Тесты: meaningful unit seams DraftSession, calendar/interaction, day-route/day-program/review, timezone validation и pricing regression. Backend API/DB roundtrip на отдельной PostgreSQL проверяет поля/UUID/version/duplicate/delete и auth/date guards. Browser E2E работает с настоящим API/БД; map provider requests могут быть детерминированно stubbed только в тесте, auth/storage/save не мокаются для основного сценария. Проверяем статус сохранения до/после ответа, запоздалые ответы, несохранённую последнюю revision. Screenshots desktop/tablet; визуальная проверка композиции.

Запустить backend pytest/Ruff, frontend Vitest/lint/typecheck/build, clean migration для schema changes, compose rebuild/start и релевантные browser regression (старый конструктор/карты/календарь/новый wizard). Результаты и точные ограничения в acceptance.md и итоговом коротком отчёте. Существующие тесты не ослаблять ради зелёного результата.

Работоспособность проверять после каждого логического изменения и перед его коммитом: релевантные тесты плюс полный frontend/backend набор изменённого слоя; на красном прогоне не переходить к зависимому таску. Итоговый отчёт обязательно перечисляет переиспользованные компоненты, новые компоненты, изменения API/БД, выполненные тесты и оставшиеся ограничения.

### Детализация требований, без новых продуктовых возможностей

- R50.1/R59.1: возврат/пропуск этапов и обратное открытие builder — навигация по уже существующим данным, чтобы не запирать старые поездки и черновики.
- R49.1/R50.2: параметры URL сохраняют выбранное представление при reload; это решение интерфейса поверх существующей поездки, без отдельной capability/таблицы.
- R12.1: конкретные offset-поля и правила drag — способ выполнить требование часовых поясов с воспроизводимыми данными. Nullable additive — выбранная безопасная миграция именно этих полей, не универсальный запрет других совместимых миграций.
- R48.1/R54.1/R55.1: одна mounted session, стабильные UUID, сериализация PUT и ограниченный retry — реализации единой модели и предотвращения потери данных, а не новая функциональность.
- R62.1/R73.1/R79.1/R80.1: отдельная DB, реальные save/auth, screenshots и acceptance.md — средства доказать заданные критерии и не затронуть пользовательские данные.
- Новые библиотеки/ключи по аудиту не нужны; если реализация докажет необходимость, решение пересматривается явно, а не сужает требования.

## Границы и швы

| Модуль | Владеет | Выставляет | Прячет |
|---|---|---|---|
| Trip aggregate / DraftSession | Одна поездка, revision, version, errors | tripApi create/get/save/duplicate; DraftSession change/save/subscribe | сериализацию запросов и server reconciliation |
| Transport schedule | Местные endpoints и опциональные UTC offsets | общий schedule helper для calendar/interaction и проверки API | UTC arithmetic, legacy inference |
| Calendar / day program | Производное представление trip.days/items | TripCalendar optional visibleDayId/selectedItemId; getDayProgram(trip,dayId), reviewTrip(trip) | clipping, принадлежность дню, warnings, без persistence |
| DayRouteMap | buildDayRoute, boundary controls, map/logistics | optional layout/parts composition для central boundaries/right map, selectedItemId callbacks | provider requests/cache; без второго алгоритма границ |
| Editor / builder | Общая сессия/handlers/modal forms, six-step composition | TripEditor mode editor|builder, default editor; TripForm basic variant | этап/выбранный день URL и responsive layout |
| Pricing | Существующий backend pricing + TS preview | Calculation.days/items/total и Finances | формулы и округление; не дублировать в wizard |

Швы для тестов: существующие REST/DraftSession, buildCalendarEntries/moveEvent/buildDayRoute, pricing; новый read model getDayProgram/reviewTrip только если нужен для UI, не generic framework.

## Вне рамок и открытые места

Ни одно требование брифа не отложено. Не добавляем внешние FX/booking API, новые поставщики карт, production deployment, публичный редизайн, отдельную модель itinerary или фиктивные соединительные события. Не требуются новые зависимости/ключи. Работа использует существующую конфигурацию карт; реальная подложка/маршрутизация зависят от уже настроенного провайдера.
