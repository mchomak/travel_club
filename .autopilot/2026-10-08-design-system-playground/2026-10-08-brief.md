# Исходная задача

> Записано 2026-10-08. Текст сохраняет формулировки запроса, существенные для результата.

Работай в существующем проекте Travel Club.

## ЗАДАЧА

Нужно создать внутренний Design System Playground для визуальной настройки текущей дизайн-системы сайта.

Это НЕ redesign сайта и НЕ задача по переделке существующих страниц.

Главная цель: создать отдельную внутреннюю страницу, где я смогу визуально видеть основные элементы дизайна Travel Club, менять их параметры через UI и мгновенно видеть результат. Изменения внутри Playground НЕ должны автоматически записываться в исходные CSS-файлы проекта.

Сначала изучи текущую структуру проекта; найди существующие стили, шрифты, CSS variables, компоненты и layout-правила; используй текущий сайт как источник исходных значений; визуальной базой считай существующий editorial-язык Travel Club. Не переделывай /test, /test_2, /test_3, /test_4 и другие существующие routes; не меняй их визуал без необходимости; не трогай backend, admin, constructor и unrelated routes; не внедряй Design System глобально во весь сайт на этом этапе; сначала нужен самостоятельный Playground. Не добавляй кнопку SAVE TO PROJECT; не создавай API для записи файлов; никакая настройка из Playground не должна менять исходники проекта автоматически.

## 1. ROUTE

Создай отдельный внутренний route: /design-system. Если архитектура проекта требует другой структуры маршрутов — адаптируй её, но URL должен остаться /design-system. Не добавляй ссылку на этот route в публичную навигацию Travel Club. Это внутренний инструмент разработки.

## 2. АУДИТ

Перед реализацией найди используемые сейчас font-family, font-weight, font-size, line-height, letter-spacing, цвета, border colors, spacing, section spacing, container widths, gutters, grid, image aspect ratios, кнопки, ссылки, metadata, captions и form controls. Определи повторяющиеся значения. Не выдумывай новую дизайн-систему там, где уже существует работающий визуальный язык. Если одинаковый элемент реализован немного по-разному на разных страницах, выбери значение, которое лучше соответствует текущей базе /test_2 и общей editorial-концепции сайта. Перед изменением кода кратко зафиксируй, какие стили найдены, какие значения будут вынесены в tokens и какие несогласованности существуют. Не останавливай работу ради моего подтверждения, если нет критического конфликта.

## 3. DESIGN TOKENS

Создай отдельный слой design tokens, предпочтительно styles/design-tokens.css или эквивалентное место, соответствующее текущей архитектуре проекта. Используй CSS Custom Properties. Начальные значения извлеки из текущего сайта.

Базовая зафиксированная палитра Travel Club: Cloud #F2F0EA; Ink #171717; Shanghai / China #163A5F; Thailand #27493B; Ocean #627F92; Madagascar #7D3027; Tobacco #7C5A3B. Если текущий сайт использует дополнительные нейтральные оттенки, borders или функциональные цвета — тоже покажи их, но не создавай лишнюю палитру без причины.

## 4. TYPOGRAPHY

Текущий визуальный принцип Travel Club: editorial serif + modern grotesk. Сначала проверь реальные font imports проекта. Не заменяй существующие шрифты другими. В Playground нужны роли DISPLAY XL, DISPLAY L, H1, H2, H3, LEAD, BODY, BODY SMALL, METADATA, CAPTION, BUTTON / CTA. Для каждой роли должно быть возможно визуально менять font family, если в проекте есть несколько разрешённых семейств; font size; line-height; font weight; letter-spacing. Используй slider + numeric input там, где это удобно. Изменение должно применяться моментально к preview. Размеры должны поддерживать отдельно как минимум desktop и mobile, если текущая система использует разные значения. Не создавай по отдельному стилю для каждого конкретного текста сайта; используй семантические typography roles.

## 5. COLORS

Покажи CORE: Cloud, Ink, основные neutral/border цвета текущего сайта. Покажи DESTINATION: China, Thailand, Ocean, Madagascar, Tobacco. Для каждого цвета нужны название, HEX, color picker, текстовое поле HEX, визуальный swatch. Изменение цвета должно сразу отражаться в preview.

## 6. SPACING

Создай управляемые spacing tokens: XS, S, M, L, XL, 2XL. Отдельно покажи section spacing, block spacing, column gap, page horizontal padding, editorial gutter. Не нужно выводить десятки случайных margin/padding. Покажи визуально разницу между значениями.

## 7. LAYOUT / GRID

Покажи и позволь настраивать max container width, page horizontal padding, number of columns, column gutter, section spacing, content width, narrow text width. Основная логика Travel Club — editorial grid примерно на 12 колонок. Добавь SHOW GRID ON / OFF. Grid overlay должен быть служебным и не менять сам layout.

## 8. TYPOGRAPHY SCALE PREVIEW

Не делай просто таблицу вроде H1 — 72px / H2 — 48px. Нужно визуально показать реальные примеры: TRAVEL CLUB; Куда — важно. С кем — важнее.; FIELD NOTES / 2026; THAILAND ’26; Города разные. Люди — свои.; Небольшие групповые путешествия, индивидуальные маршруты и поездки под ключ. Metadata и captions тоже должны быть показаны на реальном контенте.

## 9. EDITORIAL PRIMITIVES

Покажи editorial section label, issue number, year, metadata row, route, coordinates / location-style metadata, caption, thin rule, section index, large serif statement, large grotesk title, small uppercase metadata, editorial link / arrow CTA. Не создавай декоративные элементы, которых сейчас нет на сайте.

## 10. COMPONENTS

Покажи primary text CTA, secondary editorial link, arrow treatment, hover, focus. Покажи text input, textarea, select / choice, active, focus, disabled, error только если такая система уже нужна проекту. Покажи PRODUCT ITEM с примерами 01 МАРШРУТ, 02 ПОД КЛЮЧ, 03 В КОМПАНИИ и текстом «Мы продумываем. Вы путешествуете самостоятельно.». Покажи PHOTO FRAME. Все preview images используют fixed frame, overflow hidden, object-fit: cover.

## 11. IMAGES / FRAMES

Покажи реальные пропорции, которые используются или целесообразно выделяются из существующего сайта. Для каждого frame покажи название, aspect-ratio, пример изображения, поведение object-fit: cover. Сначала изучи текущие layout'ы и используй реально существующие пропорции. Не вводи произвольные aspect ratios только ради количества.

## 12. DESTINATION THEMES

Добавь переключатель TC, CHINA, THAILAND, MADAGASCAR. Это НЕ четыре разных дизайн-системы. Постоянными должны оставаться typography hierarchy, grid, spacing logic, component structure, base layout. Theme меняет только primary destination color, secondary accent при необходимости, preview photography, некоторые локальные editorial accents. Принцип: ONE BRAND → DIFFERENT WORLDS.

TC / default: Cloud + Ink + основной brand blue текущего сайта. China: Cloud + #163A5F + Ink. Thailand: Cloud + #27493B + #627F92. Madagascar: Cloud + #7D3027 / #7C5A3B + Ink. Не превращай themes в четыре отдельных CSS-макета.

## 13–16. LIVE PREVIEW, RESPONSIVE PREVIEW, SCOPING, STATE

Основная часть страницы должна содержать полноценный LIVE PREVIEW. Нужны controls и preview. В preview собери небольшой editorial composition: metadata; TRAVEL CLUB; hero statement; explanatory body copy; product item; photograph; Field Note; CTA; небольшой form fragment. Цель: за 5–10 секунд понять, как изменение token влияет на реальный сайт.

Добавь переключатели DESKTOP, TABLET, MOBILE. Preview должен реально показывать соответствующую ширину. Если обычное изменение width контейнера не позволяет корректно тестировать существующие media queries, используй минимальное техническое решение, при котором responsive preview действительно отражает breakpoints. Ориентировочно: Desktop — 1440; Tablet — 768; Mobile — 390. Если проект уже использует другие breakpoints — используй существующие.

Интерактивные настройки Playground НЕ должны менять глобальный :root всего сайта во время просмотра. Используй scoped CSS variables внутри preview container / preview environment. Изменение Playground не должно случайно менять sidebar самого Playground или другие существующие страницы.

Backend не нужен. API не нужен. Запись файлов не нужна. Настройки можно хранить в React state и, если это не усложняет реализацию, localStorage. Если используешь localStorage, это только browser draft; никакие исходники проекта не изменяются; Reset должен возвращать исходные design tokens; должна быть возможность очистить локальные overrides.

## 17–18. ACTIONS, UX

Добавь RESET, который возвращает исходные значения design system. Добавь COPY CSS, который генерирует и копирует CSS Custom Properties с текущими значениями. Добавь EXPORT TOKENS, который экспортирует текущие параметры в JSON-файл или позволяет скачать JSON. Можно также добавить COPY TOKENS JSON, если это не перегружает интерфейс.

Не делать SAVE TO PROJECT, WRITE TO CSS, WRITE TO FILE, APPLY TO WEBSITE, SERVER SAVE. Не создавать endpoint, который физически меняет исходники.

Нужны sticky control panel или sticky toolbar, понятные группы настроек, collapse/expand для крупных групп, numeric input рядом со slider, reset конкретного параметра или группы, если это легко реализовать, общий RESET, мгновенный preview, минимум визуального шума. Сам инструмент может быть более utilitarian, чем публичный сайт. Не нужно превращать его в ещё одну editorial landing page. Приоритет: удобство настройки.

## 19–23. ОГРАНИЧЕНИЯ И СТРУКТУРА

Не делать redesign текущего Travel Club; не менять homepage, Living Issue, /test_2, /test_3, /test_4; не менять backend, БД; не добавлять Storybook, Figma integration, тяжёлую design-system библиотеку, отдельный npm package, сложный state manager, backend persistence; не делать Save To Project; не переписывать CSS проекта автоматически.

Используй минимально достаточное решение: Next.js / React + CSS Custom Properties + React state + native inputs + localStorage только если оправдано. Не добавляй новую dependency, если задачу можно нормально решить средствами уже установленного стека. Перед установкой dependency проверь package.json.

На небольшом экране /design-system не должен полностью ломаться. На desktop controls и preview рядом. На небольших экранах controls и preview можно расположить последовательно. Не трать много времени на идеальную mobile UX внутреннего developer tool.

## 24–27. QA, REFINEMENT, DEFINITION OF DONE, ОТЧЁТ

После реализации обязательно запусти проект; проверь /design-system; убедись, что существующие routes продолжают работать; проверь browser console; проверь изменение font size, line height, color, spacing, container width, destination theme; проверь RESET, COPY CSS, EXPORT TOKENS, desktop / tablet / mobile preview; убедись, что изменение Playground не меняет существующий сайт и никакой код не пишет изменения обратно в проект. Если доступны browser / screenshot tools — сделай визуальный QA.

После реализации отдельно проверь, удобно ли сравнивать typography; хорошо ли читается control panel; не слишком ли много одновременно открытых параметров; очевидно ли, какой token сейчас меняется; видно ли изменение сразу; достаточно ли реальный preview; удобно ли переключать destination и responsive viewport; не выглядит ли Playground как случайный admin dashboard. Сделай один refinement pass после первого рабочего варианта.

Работа закончена, когда существует /design-system; существующие страницы не изменены визуально; базовые design tokens извлечены из текущего сайта; typography, цвета, spacing, layout tokens можно визуально редактировать; есть реальные editorial/component examples; есть TC / China / Thailand / Madagascar и Desktop / Tablet / Mobile; изменения видны моментально; RESET, COPY CSS и EXPORT TOKENS работают; SAVE TO PROJECT не существует; исходные CSS/TS/TSX файлы не изменяются из UI; нет backend/API для сохранения; unrelated routes не затронуты; console чистая; выполнен visual refinement pass.

В финальном отчёте кратко напиши: какие файлы созданы и изменены; какие design tokens удалось извлечь; какие противоречия в существующих стилях обнаружены; как открыть Playground; что можно менять через UI; где находятся base tokens; как работают COPY CSS и EXPORT TOKENS; подтверждение, что существующие страницы и их стили не были изменены. Не присылай большой листинг кода. Сначала реализуй и протестируй.
