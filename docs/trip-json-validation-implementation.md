# Проверка и повторный импорт JSON: состояние реализации

## Использование

1. На странице поездок выберите «Импорт JSON». При отклонении читаемого файла сохраните его как черновик. Черновик хранит исходный файл и последнюю сохранённую редакцию.
2. Если обязательные данные поездки корректны, создайте поездку из черновика. Безопасные дни, события и курсы попадут в поездку; неприменённые данные останутся в исходном JSON. Отчёт виден в черновике. Пока есть неприменённые записи, смета помечается неполной, статус `ready` и выпуск публичной ссылки блокируются. После ручной сверки каждой записи подтвердите её проверку в отчёте.
3. В поездке откройте «Проверка маршрута». Проверка относится к сохранённой ревизии: после ручного изменения сохраните поездку и выполните её снова. Предупреждения и рекомендации можно пропустить с причиной и восстановить. Сформируйте промпт по выбранным замечаниям и скачайте JSON и инструкцию.
4. Сохраните `reimport` и UUID при исправлении. В той же поездке загрузите файл через проверку маршрута, просмотрите изменения и выберите нужные. Конфликтующие изменения не применяются. Сокращение заполненных дней требует отдельного подтверждения. До применения автоматически создаётся снимок; его можно выбрать и восстановить в панели повторного импорта.

Импортируемый и экспортируемый JSON включает внутренние сведения. Перед передачей стороннему сервису проверьте, допустимо ли передавать соответствующий маршрут. Публичный токен не входит в экспорт.

## API и данные

- `POST /api/trips/import` создаёт отдельную поездку; `GET /api/trips/{id}/validation` проверяет сохранённую ревизию. `POST/DELETE .../validation/ignore` управляют пропуском замечаний.
- `GET/POST /api/import-drafts`, `GET/PUT /api/import-drafts/{id}`, `POST /api/import-drafts/{id}/apply` и `POST /api/import-drafts/{id}/resolve` хранят и обрабатывают исходный документ. Применение атомарно и идемпотентно для одного черновика.
- `POST /api/trips/{id}/reimport/export`, `preview`, `apply`, `restore` и `GET .../reimport/backups` создают базовый снимок, сравнивают и выборочно применяют изменения, сохраняют резервные снимки и восстанавливают их. Снимки, черновики и причины пропуска хранятся в PostgreSQL; схема обновляется миграциями Alembic.
- `reimport` в экспортируемом формате версии 1 — необязательные метаданные. Старые документы без них можно импортировать как новую поездку; для безопасного трёхстороннего сравнения нужен новый экспорт из целевой поездки.

## Реализованные правила

Техническая проверка использует существующие Pydantic-схемы, проверку ссылок и UUID дней и событий, расписания, курсов, режимов, финансовых ограничений и изображений. При неполных данных последующие этапы явно отмечаются как не выполненные. Мягкая проекция отдельно фиксирует неприменённые записи и добавленные календарные дни; она не подставляет цену, курс, категорию или дату вместо неизвестного значения.

Бизнес-проверки обнаруживают отсутствие клиентского названия, обложки и названий дней, описание активности, ожидающую и нулевую цену, отсутствие курса, участников сверх числа поездки, отсутствие вместимости, ошибки дат и вместимости отеля, длительность за пределами поездки, точки отправления и прибытия, пересечения расписания, выход этапа за время события, пересечение этапов, отсутствие часовых смещений перелёта и признаки отдельно оплачиваемых этапов. Детальный и организованный профили дополнительно проверяют местоположение и время. Неопределённые пересечения не выдаются за доказанный конфликт; отели не сравниваются с событиями как обычные интервалы. Результат проверки ограничен 5000 замечаниями с явным предупреждением о неполной проверке.

## Ограничения

- Мягкий импорт требует корректных названия, дат, количества участников и базовой валюты. До их указания хранится исходный JSON, а не создаётся фиктивная поездка. Неизвестные категории, ошибки полей, некоторые фотографии и связи карты остаются неприменёнными; данные не переносятся автоматически после ручного исправления в исходнике.
- Отчёт о неприменённых данных и подтверждение их ручной сверки не являются автоматическим доказательством, что менеджер перенёс значения правильно. Суммы при неприменённых данных — только частичный расчёт.
- Правила полноты и логистики охватывают не все сценарии из исходного задания. Нет полноценной проверки ночёвок, запасов перед рейсом, подтверждённых маршрутов карты, поставщиков, достоверности бронирований и смысловой проверки текста. Профили имеют ограниченные различия; OpenAI API не подключён.
- Проверка сырого документа останавливается перед последующими стадиями при ошибке схемы; не все независимые ошибки содержания можно получить за один проход. Сравнение замечаний для структурно невалидного исправленного документа недоступно.
- Повторный импорт принимает только исправления, которые можно представить текущей моделью. Он не переносит из исходного JSON неприменённые поля автоматически. Неоднозначные UUID и конфликтующие изменения требуют ручной работы; автоматического разрешения конфликтов нет. При добавлении и перестановке этапов может потребоваться повторное сравнение.
- Исходный документ и сохранённая поездка экспортируются отдельно для частичной поездки; объединённый экспорт актуальной поездки с неприменённым исходником пока не реализован. Снимки хранятся без автоматической политики очистки.
- Проверка запускается при открытии или по кнопке, а также после повторного импорта; автоматический запуск перед каждым изменением статуса и выпуском ссылки для обычной полной поездки не реализован. Кнопка проверки показывает устаревший результат после несохранённого изменения.

## Проверка и развёртывание

Перед обновлением сделайте резервную копию БД. Примените миграции обычным запуском backend (`docker compose up -d --build --wait`); Compose запускает `alembic upgrade head`. Обновите приложение конструктора вместе с backend. Не удаляйте PostgreSQL volume.

Для ручной проверки используйте тестовый маршрут без реальных данных: создайте JSON с неизвестным типом события, сохраните его как черновик, создайте частичную поездку, проверьте исходник и отметку неполной сметы. Затем на отдельной полной поездке экспортируйте файл, измените название события, загрузите исправленную версию, выберите изменение и восстановите резервный снимок. Проверьте конфликт, изменив то же поле вручную после экспорта. Убедитесь, что внутренняя информация не попадает в клиентский просмотр.
