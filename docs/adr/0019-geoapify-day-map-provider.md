## Контекст
Закрытому конструктору нужны поиск мест, подложка и расстояние/время для машины, пешего хода и транспорта. Пользователь выбрал Geoapify; ключей в текущей сессии нет.

## Решение
Geoapify search/reverse/routing вызываются через защищённый FastAPI API с server-only `GEOAPIFY_API_KEY`. Отдельный `GEOAPIFY_MAPS_API_KEY` выдаётся авторизованному браузеру через runtime config и ограничивается origins/referrers. Пустые ключи — штатная ненастроенная конфигурация, без фиктивной подложки и маршрутов.

Для транспорта сначала применяется `transit`, после пустого маршрута допускается `approximated_transit`. Все транспортные оценки явно приблизительные, без гарантий расписания. Ошибки сети/квоты не запускают fallback. Непрерывная проверенная GeoJSON-геометрия нормализуется в LineString; неверные ответы не создают выдуманные связи.

Полные Google Maps URL разбираются без сети; координаты камеры не считаются местом. Короткие ссылки раскрываются только по строгому allowlist и публичному DNS с привязкой соединения к проверенному IP, Host/SNI и обычной TLS-проверкой, максимум три перехода. Тело HTML не разбирается. Нераспознанное место требует поиска или ручного пина.

## Почему
Разделение ключей позволяет ограничить браузер и backend разными правилами. Стабильные DTO скрывают provider payload и секрет; ограничения ответов/таймаутов защищают приложение от неконтролируемых данных. URL resolver не становится произвольным HTTP proxy.

## Последствия
По согласованному D01 только backend получает отдельную исходящую bridge-сеть `maps_egress` в deploy Compose. PostgreSQL/frontend остаются в `app` (`internal:true`), порты не добавляются. Это корректирует прежнюю полную изоляцию для внешнего API, без выполненного серверного deploy.

Ключи добавляются локально, после изменения env нужен recreate backend, frontend rebuild не требуется. Live-проверки качества/квот/origins/egress IP остаются до настройки аккаунта. Инструкция — `docs/geoapify-setup.md`; финансовая модель, клиентский preview и существующие данные не изменены.
