# ADR 0001: Детерминированный расчёт поездки и распределение проживания

Статус: принято. Основание: `spec.md` §§9–15, 21, 28–30 и уточнения G2/D01; `manifest.md` D01 (R254, R255, R469).

## Контекст

Все три продукта Travel Club опираются на одну себестоимость поездки. Девять типов услуг допускают семь способов расчёта, валютную нормализацию и включение/исключение из сметы. Клиенту нужен мгновенный предварительный итог, но финансовый результат при сохранении должен определять сервер. Распределение гостиничного итога по ночам не должно добавлять расходы повторно. Обычное округление равной доли может сделать остаток последней ночи отрицательным, если очень маленькая сумма приходится на много ночей.

## Решение

- Одна чистая серверная функция `calculate_trip(TripInput) -> Calculation` применяет семь формул и порядок округления HALF_UP: сначала исходная стоимость статьи до 0,01, затем умножение на курс и округление нормализованной стоимости до 0,01. Денежные вычисления используют `Decimal`, хранение — `NUMERIC`, значения в JSON — строки. Режим наценки и режим целевой маржинальности имеют разные явные формулы.
- Клиентская `calculateTrip(TripInput) -> Calculation` служит только мгновенным прогнозом. Она использует десятичную арифметику и те же общие контрольные JSON-векторы, включая границы вместимости, FX, округление и нулевые суммы. Сохранённый ответ сервера авторитетен.
- Итог поездки складывается из нормализованных включённых статей ровно один раз. Дневная смета и общие расходы — распределение этого итога, а не дополнительные статьи. Исключённый элемент сохраняет снимок расчёта, но не влияет на сумму.
- Распределение по ночам определяется `calculation_mode=hotel`, независимо от типа услуги; категория остаётся категорией исходного типа. Гостиница в режиме fixed/manual целиком относится к выбранному дню либо общим расходам. День выезда не получает ночную долю.
- **D01:** для нормализованной неотрицательной суммы `T` и `n > 1` ночей доля первых `n−1` ночей равна `min(HALF_UP(T/n, 0,01), floor(T/(n−1), 0,01))`. Последняя ночь получает `T − доля × (n−1)`. При `n=1` она получает `T`. Так `.02/4` распределяется как `0, 0, 0, .02`, а `.03/5` — как `0, 0, 0, 0, .03`.

## Почему (отклонённые альтернативы)

Округление суммы только в конце меняет исторические снимки статей и делает дневные суммы неустойчивыми. Расчёт через бинарные числа создаёт расхождения на копейках. Отдельные калькуляторы для каждого типа дублируют формулы при возможности выбрать любой режим. Простое округление `T/n` для первых ночей без ограничения отвергнуто: при `T=.02`, `n=4` оно даёт три раза `.01` и остаток `−.01`. Распределение по `type=hotel` отвергнуто уточнением G2: тип и формула независимы.

## Последствия

Любое изменение людей, режима, дат, курса или включения статьи пересчитывает зависимые суммы. Общие Python/TypeScript-векторы должны проверять совпадение до цента и инвариант `сумма дней + general_total = cost_total`, в том числе `.02/4` и `.03/5`. UI не должен подменять серверный итог локальным при расхождении.
