## Контекст

Длинный список типов пункта мешает быстро добавить событие. Новые варианты еды и транспорта должны сохраняться в поездке, а старые записи с типами `train_bus`, `rental`, `insurance` и `excursion` должны оставаться доступными и рассчитываться как прежде. Добавление `meal` расширяет исчерпывающий тип `ItemType` и все зависящие от него таблицы в UI (D01).

## Решение

В создании события показывать пять крупных категорий: перелёт, транспорт, проживание, еда, впечатления. Уточняющий выбор хранить в необязательном `subtype` пункта. Подвид не определяет формулу стоимости: её задаёт существующий режим расчёта. `meal` является отдельным типом пункта для финансовой группировки, а исчерпывающие отображения `ItemType` расширяются вместе с ним. Старые коды типов остаются допустимыми в API и отображаются в соответствующих новых категориях.

## Почему

Рассмотрен вариант заменить старые типы новыми и мигрировать все сохранённые поездки. Он отвергнут: изменение интерфейса тогда затронуло бы исторические сметы и усложнило проверку сохранённых данных. Также рассмотрен свободный текст подвидов. Контролируемый список в интерфейсе даёт предсказуемый выбор, а отдельное поле оставляет существующую модель расчёта.

## Последствия

Типы API и базы остаются совместимыми с ранее сохранёнными поездками. При добавлении нового типа нужно синхронно расширять финансовую группировку и исчерпывающие отображения UI; компилятор TypeScript помогает обнаружить пропуск. Изменение списка подвидов не требует менять формулы стоимости.
