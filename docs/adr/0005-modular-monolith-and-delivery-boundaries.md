# ADR 0005: Модульный монолит и границы первого выпуска

Статус: принято. Основание: `spec.md` §§0–4, 20–21, 24–36.

## Контекст

Первый выпуск должен быть рабочим внутренним конструктором с надёжным хранением и расчётом. При этом будущий публичный сайт может стать визуально выразительным, а модель себестоимости должна пригодиться для других услуг. Разделение UI, API, расчёта, аутентификации и хранения требуется уже сейчас, но отдельные сервисы и внешние интеграции не решают текущую задачу.

## Решение

- Один backend на FastAPI и SQLAlchemy 2 разделяет доменный расчёт, работу с агрегатом PostgreSQL, HTTP-контракты и авторизацию. Схема развивается миграциями Alembic. Один Next.js frontend разделяет частный рабочий кабинет и лёгкие публичные заглушки; запросы `/api` идут same-origin proxy к backend.
- PostgreSQL — источник сохранённых поездок. Финансовые операции утверждает backend; TypeScript-расчёт отвечает за мгновенную обратную связь и сверяется общими векторами. Границы модулей проходят по ответственности, а не по каждому типу услуги: одна гибкая модель элемента допускает девять типов и семь режимов расчёта.
- Локальный запуск — Docker Compose с frontend, backend и PostgreSQL, named volume, конфигурацией через `.env` и безопасным `.env.example`. Миграции применяются до API. Первый администратор создаётся локально с защищённым вводом.

## Почему (отклонённые альтернативы)

Микросервисы, очереди, CRM, платежи, booking и автоматические цены/FX добавляют операционные границы без текущей потребности. Девять специализированных подсистем услуг дублируют правила и мешают переключать расчёт. Богатое видео, 3D и тяжёлые эффекты в админке замедляют ежедневную работу; публичная группа остаётся отдельной точкой будущего расширения.

## Последствия

Первый выпуск проверяется на реальной PostgreSQL: миграции чистой базы, backend unit/API-тесты, frontend unit/lint/typecheck/build и браузерные сценарии login/create/edit/reopen/preview/mobile. Публичные страницы честно обозначают будущие функции, не имитируя оплату и бронирование. Развитие публичного дизайна и групповых продуктов не требует переписывать расчёт или ослаблять защиту кабинета.
