# ADR 0006: Распределение многодневных услуг по дневной смете

Статус: принято. Основание: `spec.md` §13 и нормативное уточнение G4/D02; `manifest.md` D02 (R253, R255, R552).

## Контекст

Формулы `per_day` и `per_person_per_day` считают стоимость услуги за `duration_days` дней. Слепая приёмка обнаружила расхождение: общий итог был верным, но вся стоимость такой услуги попадала в первый день. Из-за этого дневная смета не отражала фактическую длительность. При распределении очень маленькой суммы обычное округление равной доли может также дать отрицательный остаток в последний день.

## Решение

- Если у элемента с `calculation_mode=per_day` или `per_person_per_day` задан `day_id`, датой начала служит дата выбранного дня. Его **нормализованная стоимость после расчёта и округления статьи** распределяется ровно на `duration_days` последовательных календарных дней, включая дату начала. Длительность должна целиком помещаться в диапазон поездки; противоречащий ввод отклоняется понятной ошибкой.
- Для суммы `T` и `n=duration_days > 1` применяется безопасный метод D01: доля каждого из первых `n−1` дней равна `min(HALF_UP(T/n, 0,01), floor(T/(n−1), 0,01))`; последний день получает `T − доля × (n−1)`. При `n=1` выбранный день получает всю сумму. Остаток всегда неотрицателен, а сумма долей точно равна `T`.
- Доли попадают в дневную группу по исходному **типу** элемента. Если `day_id=null`, статья остаётся одним общим расходом независимо от `duration_days`; в дневные группы она не распределяется. Дневные доли служат только представлением первичной стоимости: `cost_total` складывается из включённых статей один раз, без повторного добавления долей. Для `included=false` статья не даёт вклада ни в дни, ни в общий итог.
- Правило применяется по режиму расчёта, а не по названию типа услуги. Распределение `calculation_mode=hotel` по ночам и исключение дня выезда остаются отдельным правилом; прочие режимы относятся к назначенному дню или общим расходам.

## Почему (отклонённые альтернативы)

Отнесение всей многодневной стоимости к дню начала оставляет следующие дни с заниженной сметой, хотя услуга действует и там; именно этот дефект выявлен приёмкой. Деление по всему диапазону поездки неверно, если услуга начинается позже или длится меньше поездки. Добавление дневных долей поверх полной стоимости элемента даёт двойной учёт. Простая равная доля с HALF_UP без ограничения D01 может сделать последнюю долю отрицательной. Неявно обрезать длительность на последнем дне поездки нельзя: это скрыто меняет смысл введённой услуги.

## Последствия

Инвариант расчёта: сумма всех дневных групп плюс `general_total` равна `cost_total` до копейки; отдельная сумма по элементу не меняется от способа показа. При переносе элемента на другой день или изменении длительности, участников, количества либо курса дневные доли пересчитываются. Серверный Python-расчёт и предварительный TypeScript-расчёт используют одинаковый метод и общие контрольные векторы; HTTP API и браузерные проверки подтверждают каждую затронутую дату, общую сумму и отсутствие двойного учёта.
