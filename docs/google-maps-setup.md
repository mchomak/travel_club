# Подготовка Google Maps для конструктора поездок

Актуальность: 16 октября 2026. Эта инструкция готовит аккаунт Google Cloud; карта и маршруты **ещё не интегрированы** в приложение. В текущих `.env.example` и Compose нет поддерживаемых Google-переменных. Добавление ключа в случайную переменную сейчас ничего не подключит.

## 1. Создать отдельный проект

1. Откройте [Google Cloud Console](https://console.cloud.google.com/), войдите в свой аккаунт.
2. В верхнем переключателе проектов выберите **New project / Создать проект**.
3. Назовите проект **Travel Club** и создайте его. Сверху убедитесь, что выбран именно этот проект.
4. В **Billing / Оплата** лично создайте или выберите подходящий billing account и свяжите его с проектом. Пользователь выбрал страну оплаты **США (United States)**; выбирайте её при создании профиля только если она соответствует фактическим платёжным данным. Введите собственные настоящие данные. Возможность регистрации и успешная привязка оплаты в этом аккаунте ещё не проверены.

Биллинг и платёжные данные вводит владелец аккаунта. Не отправляйте номера карт, ключи или фотографии платёжных форм в чат. Полноценные Routes требуют подготовки аккаунта и биллинга. В документации Maps JavaScript также описан отдельный Demo Key для ограниченных прототипов; он не заменяет полноценную интеграцию конструктора. [Подготовка Maps JavaScript](https://developers.google.com/maps/documentation/javascript/get-api-key), [подготовка Routes](https://developers.google.com/maps/documentation/routes/get-api-key).

## 2. Включить API

В выбранном проекте откройте **APIs & Services → Library**, найдите и включите:

- **Maps JavaScript API** — интерактивная карта с нашими точками и маршрутами.
- **Places API (New)** — поиск и получение сведений о выбранном месте.
- **Routes API** — расстояния и время между местами.

**Geocoding API** включать только если реализация потребует отдельного преобразования адресов в координаты. Старые Directions API / Places API (Legacy) для этой новой интеграции подключать не нужно. Включение API само по себе не означает, что приложение уже умеет его использовать. [Начало работы Maps JavaScript](https://developers.google.com/maps/documentation/javascript/get-api-key), [Routes](https://developers.google.com/maps/documentation/routes/get-api-key).

## 3. Создать отдельные браузерный и серверный ключи

Откройте **APIs & Services → Credentials → Create credentials → API key**. Для каждого ключа откройте редактирование, задайте ограничения и сохраните. Секретные значения храните у себя; в чат достаточно сообщить, что ключи созданы. Не добавляйте их в Git, документы или screenshots.

### Браузерный ключ: Travel Club Web Local

- **Application restrictions → Websites / HTTP referrers**.
- Разрешите `http://localhost:3000/*`.
- `http://localhost:3001/*` добавляйте только если действительно используете dev-сервер на этом порту.
- В **API restrictions → Restrict key** выберите **Maps JavaScript API**. **Places API (New)** добавьте этому ключу, если поиск будет выполняться браузерным SDK. Не разрешайте браузерному ключу серверный Routes REST API.
- Production-origin добавляется отдельно после подтверждения настоящего адреса сайта; разрешение всех сайтов `*` не требуется.

Браузерный ключ виден пользователю в сетевых запросах по назначению. Его защищают ограничениями сайтов и API. Серверный ключ должен оставаться секретным. [Рекомендации Google по защите ключей](https://developers.google.com/maps/api-security-best-practices).

### Серверный ключ: Travel Club Backend

- В **API restrictions → Restrict key** разрешите **Routes API**. **Places API (New)** добавьте только если запросы Places будут идти через backend; Geocoding — только при фактическом использовании.
- **Application restrictions → IP addresses** настраиваются по реальному стабильному **публичному исходящему IP** backend, который видит Google. Это не `localhost`, не `127.0.0.1` и не внутренний IP Docker-контейнера.
- Если исходящий IP пока неизвестен или меняется, окончательная настройка серверного ключа остаётся незавершённой. Сначала определите подходящий стабильный egress либо согласуйте поддерживаемый способ авторизации; не подставляйте выдуманный адрес. До завершения ключ не используйте в production.

Браузерные referrer-ограничения не подходят серверным REST-запросам; для них применяется отдельный ключ с соответствующей защитой. [Официальные ограничения приложений и API](https://developers.google.com/maps/api-security-best-practices), [авторизация Routes](https://developers.google.com/maps/documentation/routes/get-api-key).

## 4. Ограничить расходы до первого рабочего запроса

1. В **Billing → Budgets & alerts** создайте бюджет для проекта Travel Club с небольшой приемлемой суммой и уведомлениями на свой email. Это контроль расходов, **не автоматическое прекращение тарификации**.
2. В **Google Maps Platform / APIs & Services → Quotas** проверьте доступные квоты каждого включённого API. Установите небольшие ограничения запросов в минуту; дневные — только если такая редактируемая квота действительно доступна для данного API. Не считать наличие одинакового дневного лимита у всех API гарантированным.
3. Возможный стартовый ориентир — до **250 запросов/день** для каждого реально доступного соответствующего ограничения API. За 31 день это 7750 запросов; но единицы квот могут отличаться от оплачиваемых событий, и этот ориентир не гарантирует нулевой счёт. Для Compute Route Matrix, если он позже понадобится, единицы могут быть элементами, а не HTTP-запросами.
4. В будущей реализации предусмотреть отдельный месячный мягкий порог **9000 оплачиваемых событий на каждый используемый Essentials SKU**, счётчик до отправки запроса и понятное сообщение при остановке расчётов. Сейчас такого ограничения в приложении нет. Это запас относительно бесплатных 10000, а не действующая Google Cloud настройка и не абсолютная защита от внешнего использования ключа.
5. Не использовать Pro-функции по умолчанию: пробки, оптимизацию порядка и другие расширенные параметры включать только после отдельной оценки. Следить за отчётом именно по SKU; несколько ключей одного проекта не создают дополнительные бесплатные объёмы.

Точные возможности квот нужно сверить в консоли проекта. Бюджеты, месячный счётчик приложения и API-квоты дополняют друг друга, но не дают обещания «списания невозможны». [Управление расходами Google Maps](https://developers.google.com/maps/billing-and-pricing/manage-costs), [стоимость и квоты Routes](https://developers.google.com/maps/documentation/routes/usage-and-billing), [тарифы по SKU](https://developers.google.com/maps/billing-and-pricing/pricing).

## 5. Когда подготовка закончена

Достаточно подтвердить: проект создан, страна оплаты проверена, billing account связан, три API включены, ограничения браузерного ключа сохранены, статус стабильного backend egress понятен, бюджет и доступные квоты настроены. Значения ключей передавать в чат не нужно.

После этого интеграция отдельно добавит документированные переменные окружения, передачу серверного секрета только backend и браузерного ключа frontend, поля поиска / Google Maps-ссылки, карту выбранного дня и расчёт участков. Имена будущих env-переменных и способ передачи в Docker будут закреплены в коде и `.env.example`; пока их нет.
